وثيقة تطوير المشروع Infrastructure Manager منصة ويب لإدارة ومراقبة
البنية التحتية باستخدام Python Django وDjango Templates وAnsible

الإصدار: وثيقة متطلبات وتصميم أولية التاريخ: 03-11-2026

====================================================================== 1.
تعريف المشروع
======================================================================

اسم المشروع: Infrastructure Manager

الهدف: تطوير منصة ويب مركزية لإدارة ومراقبة خادم Ubuntu والخدمات
المستضافة عليه، من خلال واجهة رسومية يمكن الوصول إليها عبر IP أو نطاق
داخلي، مع استخدام Ansible لتنفيذ مهام الأتمتة بصورة مضبوطة وآمنة.

المشروع امتداد للمجلد الحالي ansible-project، وليس مشروعاً بديلاً عنه. يجب
المحافظة على ملفات Ansible الحالية والاستفادة منها.

التقنيات الأساسية: - Python 3. - Django. - Django Templates. - HTML5
وCSS3 وJavaScript. - Bootstrap أو Tailwind CSS (اختر إطاراً واحداً وطبقه
بصورة موحدة). - PostgreSQL لتخزين بيانات المنصة عند اعتماد الإنتاج. -
Ansible لتنفيذ الأتمتة. - Docker API أو Ansible لإدارة Docker. -
Prometheus وNode Exporter للمراقبة عند دمجهما. - Traefik للنشر وReverse
Proxy عند الحاجة.

لا تستخدم React في هذه النسخة؛ المطلوب واجهة Django Templates تقليدية
وديناميكية، مع JavaScript لتحسين التفاعل دون تحويل المشروع إلى SPA.

======================================================================
2. المبادئ العامة
======================================================================

-   تصميم احترافي قابل للتوسع والصيانة.
-   الالتزام بمبادئ SOLID وDRY وKISS.
-   فصل Views عن Business Logic.
-   وضع منطق إدارة الأنظمة في Services.
-   استخدام Forms وValidators للتحقق من المدخلات.
-   استخدام Models لتخزين الإعدادات وسجلات العمليات.
-   استخدام Django permissions وGroups.
-   استخدام CSRF protection وAuthentication.
-   كتابة اختبارات للوحدات والعمليات الحساسة.
-   عدم تنفيذ أوامر Shell حرة من مدخلات المستخدم.
-   عدم كشف Docker Socket أو مفاتيح النظام للمتصفح.
-   عدم تعديل أو حذف موارد البنية الحالية تلقائياً.
-   جميع العمليات الحساسة تتطلب صلاحيات وتأكيداً وتسجيل تدقيق.

عرض Networks وVolumes بصورة قراءة أولاً. - منع الحذف افتراضياً. - أي عملية
حذف تحتاج صلاحية منفصلة وتأكيداً صريحاً وتحذيراً من أثرها. - عدم حذف
Volumes أو Networks تلقائياً.

4.5 PostgreSQL Manager - عرض خوادم/حاويات PostgreSQL. - الإصدار والمنفذ

4.11 Logs Manager - عرض سجلات الحاويات والخدمات. - اختيار الخدمة والفترة

Infrastructure Administrator. - Operator. - Monitoring Viewer. - Backup

سجل التدقيق يجب أن يسجل: - المستخدم. - العملية. - المورد المستهدف. - وقت

الأسرار.

5. الربط بين Django وAnsible
======================================================================

يجب بناء طبقة خدمة مستقلة، مثال:

    services/ansible/

وتحتوي على مسؤوليات مثل: - AnsibleRunner. - PlaybookRegistry. -
InventoryManager. - JobResultParser. - TaskValidationService.

آلية العمل: 1. يرسل المستخدم طلباً من صفحة الويب. 2. يتحقق Django من
تسجيل الدخول والصلاحيات. 3. تتحقق Form/Validator من البيانات. 4. تتحقق
Service من أن العملية مسموحة وأن المورد ضمن Inventory. 5. ينفذ Ansible
Playbook مع متغيرات محددة ومتحقق منها. 6. تحفظ المنصة نتيجة التنفيذ. 7.
تعرض الواجهة حالة المهمة ومخرجاتها المنقحة.

ضوابط التنفيذ: - لا تستخدم subprocess مع نصوص Shell مركبة من إدخال
المستخدم. - استخدم subprocess بقائمة argv أو Ansible Runner بعد دراسة
اعتماده. - لا تسمح بإرسال مسار Playbook عشوائي من المتصفح. - لا تسمح
بإرسال أمر Shell حر. - استخدم قائمة Playbooks معتمدة. - تحقق من أسماء
الحاويات والخدمات من قاعدة بيانات أو Inventory موثوق. - ضع مهام التنفيذ
الطويلة في Background Worker بدلاً من إبقاء طلب HTTP مفتوحاً. - حدد
Timeout وقيود التزامن. - سجل كل عملية. - افصل مهام القراءة عن مهام
التغيير. - العمليات الخطرة تحتاج تأكيداً إضافياً.

8. النشر والوصول عبر IP
======================================================================

يجب أن تعمل المنصة على الشبكة المحلية عبر IP الخادم.

مثال توضيحي: http://SERVER-IP:8000

في التطوير: python manage.py runserver 0.0.0.0:8000

في الإنتاج: - استخدام Gunicorn أو Uvicorn وفق التطبيق. - استخدام Traefik
أو Nginx كـ Reverse Proxy. - إعداد HTTPS. - ضبط ALLOWED_HOSTS. - ضبط
CSRF_TRUSTED_ORIGINS. - فتح المنفذ المطلوب فقط في Firewall. - عدم كشف
لوحة الإدارة للعامة دون حماية مناسبة. - لا تثبت IP الخادم في الكود؛
استخدم إعدادات البيئة.

فحص أسماء الحاويات وملفات Compose وVolumes دون تعديلها. - تحديد
Playbooks التي تم اختبارها فعلياً. - لا تفترض وجود docker.yml قبل التحقق
من الملف.

المرحلة 1: تأسيس Django - إنشاء مشروع Django منظم. - إنشاء التطبيقات
الأساسية. - إعداد settings منفصلة للتطوير والإنتاج. - إعداد قاعدة بيانات
المنصة. - إعداد تسجيل الدخول والمستخدمين والصلاحيات. - إنشاء Base
Template والقائمة والتنقل. - إعداد واجهة عربية/إنجليزية.

المرحلة 2: Dashboard وقراءة الحالة - ربط Docker للقراءة فقط. - عرض
الحاويات والحالة والمنافذ. - عرض Odoo 17 و19 بصورة منفصلة. - عرض مشاريع
Django. - عرض PostgreSQL وRedis. - إنشاء سجل للبيانات ووقت آخر تحديث.

المرحلة 3: ربط Ansible - بناء AnsibleRunner. - إعداد Playbooks معتمدة. -
إضافة عرض نتائج المهام. - إضافة صلاحيات التشغيل. - اختبار عمليات القراءة
أولاً. - إضافة التشغيل والإيقاف وإعادة التشغيل بعد مراجعة السلامة.

المرحلة 4: المراقبة - دمج Prometheus وNode Exporter. - عرض CPU وRAM
وDisk وNetwork. - إضافة Health Checks. - بناء نظام التنبيهات.

المرحلة 5: النسخ الاحتياطي - إعداد نسخ PostgreSQL. - إعداد نسخ ملفات
المشاريع. - الجدولة وسياسة الاحتفاظ. - اختبار سلامة النسخ والاستعادة في

المرحلة 6: Traefik - قراءة إعدادات Traefik. - عرض النطاقات وRouters

المرحلة 7: الإنتاج - إعداد Gunicorn/Uvicorn. - إعداد Reverse Proxy

المنصة. - اختبار الصلاحيات. - اختبار الاستعادة. - توثيق التشغيل

مقصودة.

11. المطلوب من مساعد البرمجة AI أثناء التطوير
======================================================================

اقرأ المشروع الحالي أولاً قراءة كاملة، ولا تبدأ بإنشاء ملفات أو تعديلها
قبل فهم الهيكل والملفات الموجودة.

تعليمات إلزامية: 1. افحص مجلد ansible-project وملفاته الحالية. 2. احتفظ
بجميع Playbooks التي تم اختبارها. 3. لا تستبدل إعدادات Ansible دون سبب
موثق. 4. افحص بيئة Docker الحالية بوضع القراءة فقط. 5. لا توقف أو تعيد
تشغيل أو تحذف أي حاوية أثناء مرحلة الفحص. 6. لا تحذف Volumes أو Networks
أو قواعد بيانات. 7. لا تغير منافذ الخدمات الحالية. 8. لا تفترض أن كل
الحاويات المتوقفة غير مهمة. 9. أنشئ خطة تنفيذ قبل التعديل. 10. نفذ
التطوير على مراحل صغيرة. 11. بعد كل مرحلة شغّل الاختبارات واعرض الملفات
التي تغيرت. 12. وثق أي متطلب غير متوفر بدلاً من اختلاق بيانات. 13. استخدم
Django Templates، ولا تحول الواجهة إلى React أو SPA. 14. افصل Business
Logic في Services. 15. اكتب اختبارات للصلاحيات والعمليات الحساسة. 16.
اجعل العمليات الخطرة معطلة افتراضياً إلى أن يتم اعتمادها. 17. لا تضع
كلمات مرور أو Tokens أو مفاتيح خاصة في الكود أو Git. 18. قدم تعليمات
تشغيل وتحديث واستعادة واضحة.

المخرجات المطلوبة من المساعد: - مشروع Django منظم وقابل للتوسع. - واجهة
ويب تعمل عبر IP. - ربط آمن مع Ansible. - إدارة ومراقبة الخدمات
المطلوبة. - توثيق عربي واضح. - ملف .env.example دون أسرار. -
requirements واضحة. - اختبارات. - خطوات تشغيل التطوير والإنتاج. - تقرير
بالمنجز والمتبقي والمخاطر.

======================================================================
12. قرار التصميم النهائي
======================================================================

Ansible ليس واجهة المستخدم، بل محرك الأتمتة الذي ينفذ المهام على الخادم.
Django هو Backend والمنطق والصلاحيات وإدارة البيانات. Django Templates
هي واجهة المستخدم التي تعرض المعلومات وتسمح للمستخدم بطلب العمليات.
أدوات المراقبة المتخصصة توفر القياسات والتنبيهات المستمرة.

بهذا التصميم نحصل على منصة Infrastructure Manager يمكن الوصول إليها عبر
IP، مع المحافظة على بنية Odoo وDjango وDocker الحالية، وتوسيعها تدريجياً
دون إعادة بناء الخدمات الموجودة.
