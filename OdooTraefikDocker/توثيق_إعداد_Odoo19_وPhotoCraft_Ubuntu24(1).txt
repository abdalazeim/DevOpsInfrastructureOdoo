تقرير توثيقي
إعداد وتشغيل Odoo 19 على Ubuntu باستخدام Docker وTraefik
وملخص تجارب تثبيت PhotoCraft على Ubuntu 24.04

تاريخ إعداد التقرير: 1 نوفمبر 2026
رابط نظام Odoo 19:
http://odoo19.devops-odoo.com/

======================================================================
1. الهدف ونطاق التقرير
======================================================================

يوثق هذا الملف الأعمال التي ظهرت في المحادثات والسجلات المتاحة، وبالأخص:
1) إعداد خدمة Odoo 19 داخل Docker.
2) ربط Odoo 19 مع Traefik عبر شبكة Docker مشتركة.
3) توجيه النطاق odoo19.devops-odoo.com إلى خدمة Odoo.
4) اختبار الوصول المباشر واختبار الوصول عبر النطاق.
5) توثيق محاولات تثبيت PhotoCraft على Ubuntu 24.04.
6) تسجيل التجارب التي لم تنجح وأسبابها المحتملة وطريقة تشخيصها.

ملاحظة توثيقية مهمة:
هذا التقرير يميز بين النتائج المؤكدة التي ظهرت في السجلات وبين التفاصيل التي لم تظهر
في المحادثة. لذلك لا يفترض وجود أوامر DNS أو شهادات SSL أو إعدادات إضافية لم يتم
توثيق تنفيذها فعلياً.

======================================================================
2. بيئة Odoo 19 والبنية المستخدمة
======================================================================

المكونات التي ظهرت في سجل الإعداد:

- نظام التشغيل: Ubuntu.
- تشغيل الخدمات: Docker / Docker Compose.
- مسار مشروع Odoo 19:
  /opt/odoo19-enterprise
- خدمة Odoo 19 داخل الحاوية:
  المنفذ الداخلي 8069
- منفذ HTTP المنشور على المضيف:
  10019 -> 8069
- منفذ WebSocket / longpolling المنشور:
  20019 -> 8072
- الوكيل العكسي (Reverse Proxy): Traefik v3.7
- منفذ Traefik HTTP على المضيف: 80
- منفذ إدارة Traefik الظاهر في الإعداد: 10090
- شبكة Docker المشتركة مع Traefik:
  proxy
- النطاق المستخدم:
  odoo19.devops-odoo.com

الفكرة التشغيلية:
يستقبل Traefik طلب المتصفح على المنفذ 80، ويقرأ اسم المضيف
(Host: odoo19.devops-odoo.com)، ثم يمرر الطلب إلى حاوية Odoo 19 على
المنفذ الداخلي 8069. كما جرى إعداد مسار WebSocket على المنفذ الداخلي 8072.

======================================================================
3. إعداد Odoo 19 وربطه مع Traefik
======================================================================

3.1 مجلد المشروع

مسار مشروع Docker Compose الذي ظهر في المحادثة:

  /opt/odoo19-enterprise

للدخول إلى المجلد:

  cd /opt/odoo19-enterprise

3.2 شبكة Docker

المشكلة الأساسية التي ظهرت أثناء الربط هي أن حاوية Odoo كانت تحتاج إلى الانضمام
إلى شبكة Traefik المسماة proxy حتى يتمكن Traefik من الوصول إليها.

تم اعتماد وجود شبكتين للحاوية:
- شبكة default الخاصة بمشروع Compose.
- شبكة proxy المشتركة مع Traefik.

التحقق من الشبكات:

  docker network ls

فحص الحاويات والشبكات:

  docker ps
  docker inspect <اسم_حاوية_Odoo>

يجب التأكد من ظهور شبكة proxy ضمن شبكات الحاوية، وعدم حذف شبكة default
أو وحدات التخزين (volumes) الموجودة في المشروع.

3.3 إعدادات التوجيه في Traefik

الإعداد الذي جرى اعتماده من حيث المبدأ:

- Host rule:
  odoo19.devops-odoo.com
- خدمة Odoo الخلفية:
  المنفذ الداخلي 8069
- مسار WebSocket:
  المنفذ الداخلي 8072
- تفعيل proxy mode في إعداد Odoo:
  proxy_mode = True

يجب أن تكون تسميات Traefik (Docker labels) مرتبطة بخدمة Odoo 19 وبالشبكة
proxy، وأن تشير الخدمة الخلفية إلى المنفذ الداخلي 8069، وليس إلى المنفذ
المنشور على المضيف 10019.

ملاحظة:
النص الكامل لملف compose والـ labels لم يكن محفوظاً بالكامل في السجل المتاح؛
لذلك لا يعرض التقرير ملف YAML مفترضاً على أنه الملف الأصلي المستخدم.

3.4 إعادة إنشاء الخدمة بعد تعديل Compose

بعد تعديل ملف compose، تكون أوامر التحقق وإعادة تطبيق الإعداد عادة:

  cd /opt/odoo19-enterprise
  sudo docker compose config
  sudo docker compose up -d

ثم التحقق من حالة الحاويات:

  sudo docker compose ps
  sudo docker ps

لا تنفذ أوامر حذف volumes أو docker compose down -v أثناء معالجة مشكلة
الاتصال، لأن ذلك قد يؤدي إلى فقدان بيانات قاعدة البيانات أو الملفات الدائمة.

======================================================================
4. اختبارات الاتصال ونتيجة التشغيل
======================================================================

4.1 اختبار الوصول المباشر إلى Odoo 19

تم اختبار الخدمة من داخل الخادم باستخدام curl على المنفذ المنشور 10019.
النتيجة التي ظهرت كانت:

  HTTP 303

وكان ترويس التحويل يشير إلى:

  Location: /odoo

هذه نتيجة إيجابية؛ فهي تدل على أن خدمة Odoo استجابت للطلب وأعادت توجيه
المستخدم إلى مسار الواجهة /odoo. وهي تختلف عن أخطاء الاتصال أو Connection refused.

يمكن تكرار الاختبار بالأمر:

  curl -I http://localhost:10019

4.2 اختبار الوصول عبر Traefik والنطاق

بعد إضافة حاوية Odoo 19 إلى شبكة Docker المسماة proxy وضبط التوجيه عبر
Traefik، نجح اختبار الطلب الموجه باستخدام اسم المضيف، وأصبح الوصول عبر النطاق
يعمل وفق السجل المتاح:

  http://odoo19.devops-odoo.com/

النتيجة التشغيلية المؤكدة:
- Odoo 19 استجاب مباشرة على المنفذ المنشور.
- Traefik تمكن من الوصول إلى حاوية Odoo بعد ربطها بشبكة proxy.
- طلب Host الخاص بالنطاق odoo19.devops-odoo.com تم توجيهه إلى Odoo 19.

يجب ملاحظة أن الرابط الموثق هنا يستخدم HTTP. لا يفترض هذا التقرير أن HTTPS
أو شهادة TLS قد تم إعدادها، لعدم وجود نتيجة موثقة لذلك في السجل.

======================================================================
5. تجربة Odoo 17 السابقة ومشكلة 404
======================================================================

ظهرت أثناء العمل تجربة مرتبطة بخدمة Odoo 17، وهي منفصلة عن خدمة Odoo 19.

المعلومات التي ظهرت:
- المنفذ المنشور لـ Odoo 17: 10017.
- تم اختبار:
  http://localhost:10017/web/database/selector
- أعاد الاختبار المباشر HTTP 200.
- في البداية كان Traefik يعيد 404 لأن حاوية Odoo 17 كانت على شبكة default
  فقط، ولم تكن متصلة بشبكة proxy المشتركة مع Traefik.
- بعد ربط الحاوية بالشبكتين default وproxy وإضافة تسميات Host المناسبة،
  أصبح إعداد التوجيه متوافقاً مع بنية Traefik.

اسم الحاوية الذي ظهر في السجل:
  odoo-17-docker-odoo17-1

النطاق الذي كان مخصصاً لـ Odoo 17:
  odoo17.devops-odoo.com

الدروس المستفادة:
1) نجاح curl على localhost لا يضمن أن Traefik يستطيع الوصول إلى الحاوية.
2) يجب أن تكون حاوية التطبيق وTraefik على شبكة Docker مشتركة.
3) يجب أن يطابق Host rule النطاق المطلوب تماماً.
4) يجب أن يشير Traefik إلى المنفذ الداخلي للخدمة، لا إلى منفذ المضيف المنشور.

======================================================================
6. تشخيص أعطال Odoo وTraefik
======================================================================

أ) ظهور 404 من Traefik:
- افحص أن حاوية Odoo متصلة بشبكة proxy.
- افحص وجود Host rule الصحيح في labels.
- افحص أن خدمة Traefik الخلفية تشير إلى المنفذ 8069 الخاص بـ Odoo 19.
- افحص سجلات Traefik والحاوية.

أوامر مفيدة:

  sudo docker ps
  sudo docker network inspect proxy
  sudo docker logs <اسم_حاوية_Traefik> --tail 100
  sudo docker logs <اسم_حاوية_Odoo19> --tail 100

ب) ظهور Connection refused أو فشل الاتصال المباشر:
- تحقق من أن الحاوية تعمل.
- تحقق من نشر المنفذ 10019 إلى 8069.
- افحص السجلات:

  sudo docker compose ps
  sudo docker compose logs --tail 100

ج) ظهور HTTP 303:
- لا تعتبره فشلاً تلقائياً.
- افحص ترويسة Location؛ في الاختبار المسجل كانت /odoo.
- يمكن متابعة الاختبار باستخدام المتصفح أو curl مع تتبع التحويلات:

  curl -IL http://localhost:10019

د) مشكلة WebSocket:
- تأكد من توجيه WebSocket إلى المنفذ الداخلي 8072.
- تأكد من أن إعدادات Traefik الخاصة بالخدمة صحيحة.
- راجع سجلات Odoo وTraefik.

هـ) تحذير أمني وتشغيلي:
- لا تنشر منافذ الإدارة أو قواعد البيانات للعامة دون حاجة.
- لا تشارك كلمات المرور أو ملفات البيئة التي تحتوي على أسرار.
- احتفظ بنسخة احتياطية من قاعدة البيانات وfilestore قبل أي تغيير كبير.

7. توثيق تجربة تثبيت PhotoCraft على Ubuntu 24.04
======================================================================

المشروع:
  https://github.com/storytold/photocraft

المجلد الذي تم تنزيل مصدر المشروع إليه:
  ~/Public/photocraft-main

عند تنفيذ:

  ls

ظهرت ملفات ومجلدات مثل:
  Cargo.toml
  Cargo.lock
  apps
  crates
  README.md
  book
  packaging

هذا يوضح أن المجلد يحتوي على الشيفرة المصدرية للمشروع (Source Code)، وليس
بالضرورة ملف تثبيت جاهزاً بصيغة AppImage.

7.1 تثبيت مكتبات الرسوميات

تم تنفيذ تثبيت/تحديث حزم Mesa ومكتبات الرسوميات، وظهرت في سجل الطرفية
عمليات إعداد ناجحة مثل:

  mesa-libgallium:i386
  libgbm1:amd64
  libgbm1:i386
  libgl1-mesa-dri:amd64
  libgl1-mesa-dri:i386
  libegl-mesa0:amd64
  mesa-va-drivers:amd64
  mesa-va-drivers:i386
  libglx-mesa0:amd64
  libglx-mesa0:i386

وانتهى سجل مدير الحزم برسالة معالجة triggers الخاصة بـ libc-bin.
هذا يعني أن الحزم المذكورة وصلت إلى مرحلة الإعداد، لكنه لا يثبت وحده أن
PhotoCraft أصبح مثبتاً أو يعمل.

7.2 محاولات تشغيل AppImage

تمت تجربة الأوامر التالية:

  ~/Applications/PhotoCraft.AppImage
  /Applications/PhotoCraft.AppImage

وكانت النتيجة:

  No such file or directory

ثم تمت محاولة:

  chmod +x PhotoCraft.AppImage
  ./PhotoCraft.AppImage

وكانت النتيجة أيضاً أن الملف غير موجود.

سبب الفشل:
لم يكن ملف PhotoCraft.AppImage موجوداً في المجلد الحالي، كما لم يكن موجوداً
في المسارين اللذين تمت محاولة تشغيله منهما. أمر chmod لا ينشئ الملف؛ بل يغير
صلاحيات ملف موجود مسبقاً.

7.3 محاولة تشغيل الملف من مجلد المصدر

المجلد الحالي في سجل الطرفية كان:

  ~/Public/photocraft-main

وعند تنفيذ:

  ls

لم يظهر ملف باسم PhotoCraft.AppImage. لذلك فشل تشغيله من هذا المجلد أيضاً.

الاستنتاج:
تنزيل مستودع GitHub بالطريقة التي أنتجت photocraft-main لا يعني تنزيل نسخة
AppImage جاهزة. يجب تنزيل ملف التوزيعة الصحيح من صفحة Releases، أو بناء
المشروع من المصدر وفق تعليمات المشروع.

7.4 محاولة تثبيت DEB

تمت تجربة مسار تنزيل وتثبيت ملف DEB باستخدام اسم إصدار ورابط مباشر. لم تظهر
في السجل المتاح نتيجة تثبت نجاح تنزيل الملف أو تثبيته أو تشغيل التطبيق.
لذلك لا يصنف هذا التقرير محاولة DEB على أنها ناجحة.

كذلك لا ينبغي افتراض اسم ملف الإصدار أو رقم الإصدار أو رابط التنزيل. يجب أخذ
اسم الملف الفعلي من صفحة الإصدارات الرسمية للمشروع:

  https://github.com/storytold/photocraft/releases

8. الطريقة الصحيحة لتشخيص PhotoCraft عند الفشل
======================================================================

أولاً: معرفة معمارية Ubuntu:

  dpkg --print-architecture

القيم الشائعة:
- amd64: أجهزة Intel/AMD 64-bit.
- arm64: أجهزة ARM 64-bit.

ثانياً: معرفة الملفات التي تم تنزيلها:

  find ~/Downloads ~/Public -maxdepth 3 -iname '*photocraft*' -print

ثالثاً: التحقق من ملف DEB قبل تثبيته:

  ls -lh ~/Downloads/*photocraft*.deb
  file ~/Downloads/photocraft*.deb

إذا كان الملف موجوداً وصحيحاً:

  sudo apt install ~/Downloads/photocraft*.deb

رابعاً: إذا كان الملف AppImage:

  chmod +x ~/Downloads/PhotoCraft.AppImage
  ~/Downloads/PhotoCraft.AppImage

لا تنفذ الأمرين السابقين إلا بعد التأكد من وجود الملف بالاسم والمسار نفسيهما.

خامساً: إذا كان التنزيل من GitHub Releases:

- افتح صفحة Releases الرسمية.
- اختر إصداراً مستقراً/مناسباً.
- تحقق من ملفات Assets المرفقة بالإصدار.
- اختر ملف Linux المطابق لمعمارية الجهاز.
- لا تخمن اسم الملف أو رابط التنزيل اعتماداً على رقم إصدار قديم.
- بعد التنزيل تحقق من الملف باستخدام ls وfile قبل التثبيت.

سادساً: إذا كان المطلوب البناء من المصدر:
المجلد الحالي يحتوي على Cargo.toml، ما يشير إلى استخدام Rust ضمن المشروع.
لكن لا تبدأ البناء قبل مراجعة README وتعليمات البناء الرسمية، وتثبيت
المتطلبات التي يحددها المشروع. وجود Cargo.toml لا يعني أن تشغيل cargo run
من جذر المشروع هو الطريقة الصحيحة؛ فقد يكون المشروع workspace متعدد الحزم.

9. ملخص النتائج النهائية
======================================================================

Odoo 19:
- المشروع موجود في /opt/odoo19-enterprise.
- Odoo 19 يستمع داخل الحاوية على 8069.
- المنفذ المنشور على المضيف 10019.
- منفذ WebSocket الداخلي 8072، والمنفذ المنشور 20019.
- Traefik v3.7 يستخدم المنفذ 80، وظهر منفذ إدارة 10090.
- ربط حاوية Odoo 19 بشبكة proxy كان خطوة أساسية لنجاح توجيه Traefik.
- اختبار localhost أعاد HTTP 303 مع Location: /odoo.
- اختبار Host عبر Traefik نجح بعد ربط الحاوية بشبكة proxy.
- رابط الوصول المسجل:
  http://odoo19.devops-odoo.com/

Odoo 17:
- اختبار localhost على المنفذ 10017 أعاد HTTP 200.
- ظهر خطأ 404 عبر Traefik عندما لم تكن الحاوية متصلة بشبكة proxy.
- تم توثيق اسم الحاوية odoo-17-docker-odoo17-1 والنطاق
  odoo17.devops-odoo.com.

PhotoCraft:
- تم تنزيل مصدر المشروع إلى ~/Public/photocraft-main.
- تم إعداد بعض مكتبات Mesa بنجاح.
- لم يكن PhotoCraft.AppImage موجوداً في المسارات التي تمت تجربتها.
- لذلك فشلت أوامر chmod والتشغيل بسبب عدم وجود الملف.
- محاولة DEB لم تتوفر لها نتيجة نجاح مؤكدة في السجل.
- لا يوجد في المعلومات المتاحة ما يثبت نجاح تشغيل PhotoCraft حتى تاريخ التقرير.
