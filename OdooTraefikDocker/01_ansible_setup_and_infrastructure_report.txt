تقرير توثيقي شامل مشروع إعداد Ansible وتجهيز البنية التحتية لإدارة خوادم
Docker وOdoo وDjango تاريخ إعداد التقرير: 03-11-2026

====================================================================== 1.
الهدف العام من العمل
======================================================================

بدأ العمل بتجهيز Ansible على خادم Ubuntu ليكون أداة مركزية لأتمتة إدارة
الخدمات الموجودة على الخادم، مع الحفاظ على الأنظمة الحالية وعدم إعادة
تثبيتها أو تغيير قواعد بياناتها.

الهدف الحالي هو الانتقال تدريجياً من أوامر الإدارة اليدوية إلى Playbooks
منظمة، ثم تطوير منصة ويب خاصة لإدارة البنية التحتية باستخدام Python
وDjango وTemplates.

المكونات التي يراد إدارتها مستقبلاً: - حاويات Docker. - Odoo 17 وOdoo 19،
كل إصدار بصورة مستقلة. - مشاريع Django متعددة. - PostgreSQL. - Redis. -
موارد الخادم: CPU وRAM والتخزين والشبكة. - النسخ الاحتياطي لقواعد
البيانات والملفات. - مراقبة الخدمات والتنبيه عند توقفها. - Traefik
والنطاقات وشهادات SSL. - سجلات التشغيل والأخطاء.

مبدأ أساسي: يجب أن تكون المنصة إدارية وآمنة، وألا تنفذ عمليات حذف أو
إعادة تشغيل أو تعديل على الخدمات الحساسة دون طلب صريح وتأكيد مناسب.

======================================================================
2. بيئة الخادم
======================================================================

نظام التشغيل: - Ubuntu 24.04. - بيئة Linux Server محلية متصلة بالشبكة. -
اسم المضيف المستخدم في سياق العمل: devops-odoo. - المستخدم الظاهر في
الطرفية: odoo.

ملاحظة الشبكة: - المطلوب لاحقاً إتاحة واجهة الإدارة من خلال عنوان IP
الخاص بالخادم. - لا ينبغي تثبيت عنوان IP داخل ملفات التطبيق؛ الأفضل
الاستماع على واجهة الشبكة المناسبة، ثم الوصول باستخدام عنوان الخادم
الحالي. - يمكن لاحقاً ربط اسم نطاق داخلي أو إعداد HTTPS عبر Traefik.

======================================================================
3. تثبيت Ansible
======================================================================

تم تثبيت Ansible على Ubuntu 24.04 باستخدام مستودع PPA الخاص بـ Ansible.

الأوامر التي استخدمت في عملية التثبيت:

    sudo apt update
    sudo apt install software-properties-common -y
    sudo add-apt-repository --yes --update ppa:ansible/ansible
    sudo apt install ansible -y

التحقق من التثبيت:

    ansible --version

النسخ التي ظهرت في سجل العمل: - Ansible core: 2.21.5 - Ansible package:
14.5.0 - Python: 3.12.3

ملاحظة حول APT: ظهر أثناء تحديث الحزم خطأ من مستودع PostgreSQL يفيد بأن
الملف الذي تم تنزيله لا يطابق الحجم المتوقع، مع رسالة تشير إلى احتمال
تزامن المرآة (Mirror sync in progress). هذا الخطأ منفصل عن تثبيت
Ansible، ولم يتم توثيق إصلاحه في الخطوات الحالية. يجب مراجعته عند الحاجة
إلى تحديث الحزم.

======================================================================
4. إنشاء مشروع Ansible
======================================================================

تم إنشاء مجلد المشروع في المسار:

    ~/ansible-project

الهيكل الذي تم تجهيزه:

    ansible-project/
    ├── ansible.cfg
    ├── inventory/
    │   └── hosts
    ├── playbooks/
    │   ├── server_info.yml
    │   ├── odoo17.yml
    │   ├── odoo19.yml
    │   └── django.yml
    └── roles/

الغرض من المجلدات: - ansible.cfg: إعدادات Ansible الخاصة بالمشروع. -
inventory/hosts: تعريف الأجهزة المستهدفة. - playbooks/: ملفات المهام
والأتمتة. - roles/: مكان تنظيم الأدوار القابلة لإعادة الاستخدام مستقبلاً.

تم إعداد Inventory محلي لاستخدام localhost. وتم التحقق من الاتصال
بالأمر:

    ansible all -m ping

النتيجة التي ظهرت: - localhost | SUCCESS - ping: pong

وهذا يؤكد أن Ansible يستطيع تنفيذ المهام على الخادم المحلي.

تم إنشاء Playbook باسم:

وظيفته جمع معلومات عن الحاويات والخدمات الموجودة دون تعديلها.

10017 إلى المنفذ الداخلي 8069. - Longpolling: المنفذ الخارجي 20017 إلى
الداخلي 8072. - قاعدة البيانات: odoo-17-docker-db-1. - قاعدة البيانات

20019 إلى الداخلي 8072. - قاعدة البيانات: odoo19-enterprise-db-1. -

حاويات قديمة متوقفة مرتبطة بمشاريع NetBox وJenkins وDjango وخدمات أخرى.

تنبيه: لا يجوز حذف الحاويات القديمة أو تنظيف Docker أو حذف Volumes بناءً
على كون الحاوية متوقفة فقط. قد تحتوي على بيانات أو إعدادات مهمة. يجب فحص
كل حاوية وVolumes والشبكات وملفات Compose قبل اتخاذ قرار.

======================================================================
6. Playbooks الخاصة بالأنظمة
======================================================================

تم تجهيز ثلاثة ملفات Playbook مخصصة لعرض الحاويات المتعلقة بكل نظام.

أ) playbooks/odoo17.yml - يعرض حاويات Odoo 17 باستخدام مرشح الاسم:
docker ps -a –filter name=odoo-17 - يعرض بيئتي Odoo 17 Docker وOdoo 17
Community وقواعد بياناتهما.

ب) playbooks/odoo19.yml - يعرض حاويات Odoo 19 باستخدام مرشح الاسم:
docker ps -a –filter name=odoo19 - يعرض Odoo 19 Enterprise وقاعدة
بياناته.

ج) playbooks/django.yml - يعرض حاويات Django باستخدام مرشح الاسم: docker
ps -a –filter name=django - أظهر الحاوية الحالية الصحية والحاوية القديمة
المتوقفة.

تم التحقق من صحة صياغة الملفات بالأوامر:

    ansible-playbook playbooks/odoo17.yml --syntax-check
    ansible-playbook playbooks/odoo19.yml --syntax-check
    ansible-playbook playbooks/django.yml --syntax-check

النتيجة: - نجحت اختبارات Syntax Check للملفات الثلاثة.

ثم تم تشغيل Playbooks بنجاح: - ok=2 - changed=0 - failed=0

هذه الملفات في وضع عرض واستعلام، ولا تنفذ تشغيل أو إيقاف للحاويات.

======================================================================
7. خطوة إدارة Docker المقترحة
======================================================================

تم اقتراح إضافة ملف:

    playbooks/docker.yml

ليدعم عمليات عامة وفق متغير docker_action: - list: عرض الحاويات. -
start: تشغيل حاوية. - stop: إيقاف حاوية. - restart: إعادة تشغيل حاوية. -
logs: عرض آخر السجلات.

مثال العرض:

    ansible-playbook playbooks/docker.yml -e "docker_action=list"

أمثلة تشغيل عمليات على حاوية محددة:

    ansible-playbook playbooks/docker.yml -e "docker_action=logs container_name=odoo19-enterprise-odoo19-1"

يجب اعتبار هذا الملف خطوة مقترحة في التطوير، وليس جزءاً مؤكداً من التنفيذ
النهائي ما لم يتم إنشاء الملف وتشغيله والتحقق من نتائجه.

تحسينات السلامة المطلوبة قبل اعتماد هذا Playbook: - التحقق من أن
docker_action ضمن قائمة العمليات المسموح بها. - التحقق من وجود
container_name للعمليات التي تتطلبه. - التحقق من أن اسم الحاوية ضمن
قائمة مسموحة أو جلبه من Inventory موثوق. - استخدام command مع argv بدلاً
من تركيب نص أوامر غير مضبوط. - استخدام –tail عند عرض السجلات لتحديد حجم
المخرجات. - عدم تنفيذ start أو stop أو restart تلقائياً. - طلب تأكيد
إضافي للعمليات الحساسة. - عدم استخدام shell إلا عند وجود ضرورة واضحة.

مثال آمن نسبياً لعرض آخر 100 سطر من سجل حاوية:

    docker logs --tail 100 CONTAINER_NAME

يجب اختبار كل عملية على حاوية غير حرجة أولاً، وعدم اتخاذ قواعد البيانات
أو الخدمات الإنتاجية كوسيلة اختبار.

9. التصور المعماري للمرحلة التالية
======================================================================

القرار المقترح هو الإبقاء على Ansible واستخدامه كطبقة تنفيذ وأتمتة، ثم
تطوير واجهة ويب مستقلة باستخدام Python Django وDjango Templates.

المكونات:

1.  Django Backend

-   تسجيل الدخول وإدارة الجلسات.
-   إدارة المستخدمين والمجموعات والصلاحيات.
-   واجهات API داخلية عند الحاجة.
-   خدمات Python لتنفيذ عمليات الإدارة.
-   إدارة الإعدادات وسجل العمليات.

2.  Django Templates

-   واجهة HTML ديناميكية من جهة الخادم.
-   تصميم Responsive يعمل على الحاسوب والهاتف.
-   لوحة تحكم عربية وإنجليزية.
-   دعم RTL وLTR.
-   صفحات لإدارة Docker وOdoo وDjango وقواعد البيانات والمراقبة والنسخ
    الاحتياطي.

3.  Ansible

-   تنفيذ Playbooks من خلال طبقة خدمة داخل Django.
-   تشغيل المهام المعتمدة فقط.
-   إرجاع حالة التنفيذ والمخرجات إلى الواجهة.
-   عدم السماح للمستخدم بإرسال أوامر Ansible أو Shell حرة.

4.  أدوات المراقبة

-   يمكن دمج Prometheus وNode Exporter لمراقبة موارد الخادم.
-   يمكن استخدام أدوات مراقبة الخدمات والتنبيهات بحسب متطلبات التنفيذ.
-   لا تعتبر هذه الأدوات مثبتة حالياً؛ هي خيارات مقترحة للمرحلة القادمة.

5.  Docker

-   إدارة الحاويات من خلال Docker API أو Playbooks مع صلاحيات محددة.
-   يجب عدم كشف Docker Socket للمتصفح أو للواجهة الأمامية.
-   تكون كل عمليات Docker عبر Backend موثوق مع سجل تدقيق.

10. الوصول من خلال IP
======================================================================

يمكن تشغيل تطبيق Django على منفذ داخلي أو منفذ مخصص، ثم الوصول إليه من
جهاز آخر على الشبكة باستخدام عنوان IP للخادم.

مثال توضيحي فقط:

    http://SERVER-IP:8000

في بيئة التطوير يمكن تشغيل Django على:

    python manage.py runserver 0.0.0.0:8000

هذا الأمر مناسب للتطوير والاختبار فقط، وليس لتشغيل إنتاجي آمن.

في الإنتاج يجب استخدام خادم WSGI/ASGI مناسب مثل Gunicorn أو Uvicorn بحسب
بنية المشروع، مع Reverse Proxy مثل Traefik أو Nginx، وضبط ALLOWED_HOSTS
وCSRF_TRUSTED_ORIGINS والجدار الناري وHTTPS.

لا تثبت عنوان IP داخل الكود. يجب ضبط عنوان الوصول في إعدادات البيئة،
والسماح بالعناوين المعتمدة فقط.

13. الخلاصة
======================================================================

تم تجهيز أساس Ansible بنجاح على خادم Ubuntu 24.04، وتم إنشاء مشروع أولي
وInventory محلي واختبار الاتصال، كما تم اكتشاف وتوثيق مجموعة الحاويات
والخدمات الموجودة، وإنشاء Playbooks لعرض بيئات Odoo 17 وOdoo 19 وDjango.

المرحلة التالية ليست استبدال Ansible، بل بناء منصة ويب باستخدام Django
وDjango Templates تجعل Ansible محرك الأتمتة خلف الواجهة. وستوفر المنصة
واجهة مركزية يمكن الوصول إليها عبر IP، مع إدارة الخدمات والمراقبة والنسخ
الاحتياطي والتنبيهات، وفق ضوابط أمان تمنع التأثير غير المقصود على
الأنظمة الحالية.
