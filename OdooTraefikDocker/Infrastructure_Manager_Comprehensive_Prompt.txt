وثيقة البرومبت الشامل لتطوير مشروع Infrastructure Manager

الإصدار: 1.0 اللغة: العربية مع اعتماد المصطلحات التقنية الإنجليزية عند
الحاجة التقنيات الأساسية: Python, Django, Django Templates, PostgreSQL,
Ansible, Ansible Semaphore, Docker الهدف: بناء منصة ويب مركزية وآمنة
لإدارة ومراقبة البنية التحتية والخدمات المستضافة على خوادم Ubuntu.

====================================================================== 1.
الدور المطلوب من مساعد الذكاء الاصطناعي
======================================================================

أنت مهندس برمجيات ومعماري أنظمة DevOps وBackend Senior Engineer ومتخصص
في: - Python وDjango. - Linux وUbuntu Server. - Ansible وAnsible
Semaphore. - Docker وDocker Compose. - PostgreSQL وRedis. - Reverse
Proxy وTraefik وTLS/SSL. - Monitoring وLogging وAlerting. - أمن الأنظمة
وإدارة الصلاحيات والنسخ الاحتياطي.

مهمتك دراسة المشروع الحالي وملفاته وبيئة التشغيل أولاً، ثم تطويره تدريجياً
إلى منصة احترافية باسم Infrastructure Manager. لا تبدأ بإعادة كتابة
المشروع أو حذف أي ملفات قبل فهم بنيته الحالية. لا تفترض وجود وظائف أو
ملفات لم يتم التحقق منها. افحص الكود والإعدادات والاعتماديات والاختبارات
والوثائق الموجودة، ثم قدم خطة تنفيذ واضحة، وبعد اعتمادها نفّذها على مراحل
صغيرة قابلة للاختبار.

يجب أن تكون النتيجة نظاماً عملياً قابلاً للتشغيل والصيانة والتوسع، وليس
مجرد واجهات شكلية أو بيانات تجريبية.

======================================================================
2. الرؤية العامة للمشروع
======================================================================

إنشاء منصة ويب موحدة لإدارة خادم Ubuntu والخدمات والتطبيقات التي تعمل
عليه، من خلال واجهة Django مركزية. تستخدم المنصة Ansible لتنفيذ عمليات
الإدارة والأتمتة، ويكون Ansible Semaphore هو طبقة تشغيل المهام وإدارة
تنفيذ Playbooks ومتابعة سجلاتها.

المبدأ المعماري الأساسي: - Django هو Control Plane وواجهة الإدارة
الرئيسية ومنطق العمل وإدارة المستخدمين والبيانات. - Semaphore هو
Automation Execution Layer لتشغيل المهام المعتمدة ومتابعة تنفيذها. -
Ansible هو محرك الأتمتة الفعلي الذي ينفذ الإجراءات على الخوادم. - أدوات
المراقبة المتخصصة تجمع المقاييس والسجلات، ولا يُطلب من Semaphore أن يكون
بديلاً عنها. - Docker وواجهات النظام الرسمية هي مصادر الحالة الفعلية
للخدمات، ولا تعتمد المنصة على بيانات وهمية.

لا تعِد برمجة محرك Ansible داخل Django، ولا تنفذ أوامر Shell عشوائية
مباشرة من طلبات الويب. اربط Django بـ Semaphore API من خلال طبقة تكامل
مستقلة وآمنة.

3. الهيكل المعماري المستهدف
======================================================================

المستخدم | v Infrastructure Manager - Django Web Application | +–
Dashboard & Overview +– Server Management +– Docker Management +– Odoo
Management +– Django Projects Management +– Databases Management +–
Backup Management +– Monitoring & Alerts +– Network / Domains / SSL +–
Users / Roles / Audit Logs | v Integration Services | +– Semaphore REST
API +– Prometheus / Node Exporter +– Docker Engine API (عند الحاجة
وبصلاحيات مقيدة) +– PostgreSQL health and metrics +– Redis health checks
+– Notification providers | v Semaphore | v Ansible Playbooks / Roles /
Inventory / Vault | v Ubuntu Servers / Docker Hosts / Applications

يمكن أن تعمل جميع المكونات في خادم واحد في بيئة الاختبار، لكن يجب
تصميمها بحيث تدعم إضافة خوادم متعددة لاحقاً. افصل خدمات المنصة عن الخدمات
التي تديرها قدر الإمكان، ولا تجعل تعطل واجهة Django يؤدي إلى إتلاف
التطبيقات المُدارة.

======================================================================
4. مبادئ التصميم والهندسة البرمجية
======================================================================

التزم بالمبادئ التالية: - SOLID وDRY وKISS وSeparation of Concerns. -
OOP عند وجود فائدة حقيقية، مع استخدام composition بدلاً من التعقيد غير
الضروري. - تقسيم المشروع إلى Django apps مستقلة حسب المجال الوظيفي. -
فصل Models وViews وForms وServices وSelectors وTasks وAPI Clients
وValidators. - وضع منطق الأعمال في Services وليس داخل Views أو
Templates. - استخدام Django ORM والاستعلامات الفعالة، وتجنب N+1 باستخدام
select_related وprefetch_related. - استخدام transactions.atomic عند
العمليات متعددة الخطوات. - إضافة قيود قاعدة البيانات والفهارس
المناسبة. - استخدام type hints وتوثيق الدوال والخدمات المهمة. - معالجة
الاستثناءات برسائل واضحة دون كشف الأسرار أو تفاصيل النظام الحساسة. - عدم
تكرار منطق الاتصال بـ Semaphore أو Docker أو أدوات المراقبة. - توفير
اختبارات Unit وIntegration للوظائف الحرجة. - عدم وضع منطق الأعمال داخل
JavaScript أو HTML. - دعم pagination وfiltering وsearch وsorting. -
تصميم الواجهات لتكون Responsive وتعمل على الشاشات المكتبية واللوحية. -
دعم اللغة العربية RTL والإنجليزية LTR، مع إمكانية إضافة لغات أخرى. -
استخدام تصميم احترافي موحد للألوان والأيقونات والخطوط والتنبيهات
والجداول والنوافذ. - عدم إدخال مكتبات ضخمة دون مبرر واضح.

======================================================================
5. دراسة المشروع الحالي قبل التطوير
======================================================================

ابدأ بتنفيذ مرحلة Discovery فقط: 1. افحص جميع المجلدات والملفات. 2. حدد
لغة وإطار العمل المستخدمين حالياً، ونقطة تشغيل Backend وFrontend إن وجدت.
3. افحص ملفات requirements أو pyproject أو package.json أو Docker
Compose أو ملفات البيئة النموذجية. 4. افحص قاعدة البيانات الحالية وآلية
migrations. 5. افحص الاختبارات والوثائق وملفات التشغيل. 6. حدد ما يمكن
إعادة استخدامه وما يحتاج إلى تعديل. 7. اكتشف كلمات المرور أو المفاتيح أو
الأسرار المكشوفة في المستودع، ولا تطبع قيمها في التقارير. 8. افحص
المنافذ والخدمات والتعارضات المحتملة دون إيقاف أي خدمة. 9. أنشئ تقريراً
يوضح الوضع الحالي والمخاطر والفجوات. 10. اقترح خطة تطوير على مراحل، مع
قائمة الملفات التي ستنشأ أو تتغير.

ممنوع في هذه المرحلة: - حذف قواعد بيانات أو volumes. - حذف حاويات أو صور
Docker. - تغيير المنافذ الحالية دون موافقة. - تعديل إعدادات SSH أو
Firewall أو DNS أو الشبكة دون موافقة. - تشغيل أوامر destructive. - إعادة
تهيئة الخادم أو إعادة تثبيت الخدمات. - استبدال ملفات إعدادات قائمة قبل
أخذ نسخة احتياطية وفهم أثر التغيير.

بعد مرحلة الدراسة، ابدأ التنفيذ على دفعات صغيرة. بعد كل دفعة شغّل
الاختبارات المناسبة واعرض ملخصاً للتغييرات والنتائج.

======================================================================
6. الوحدات الرئيسية في Django
======================================================================

أنشئ تطبيقات مستقلة، ويمكن تعديل الأسماء بما يتوافق مع المشروع الحالي:

1.  core
    -   الإعدادات العامة، الصفحة الرئيسية، أدوات مشتركة، صفحات الأخطاء.
    -   إعدادات اللغة والمنطقة الزمنية والتنسيق.
    -   سجل أحداث النظام العام.
2.  accounts
    -   المستخدمون والمجموعات والأدوار والصلاحيات.
    -   تسجيل الدخول والخروج وإدارة الجلسات.
    -   سياسة كلمات المرور والحماية من محاولات الدخول المتكررة.
    -   تعطيل الحسابات وإدارة المستخدمين النشطين.
    -   صلاحيات دقيقة حسب الوحدة والإجراء والخادم.
3.  dashboard
    -   لوحة معلومات عامة.
    -   حالة الخوادم والخدمات.
    -   ملخص CPU وRAM وDisk وNetwork.
    -   عدد حاويات Docker وحالاتها.
    -   حالة Odoo وقواعد البيانات ومشاريع Django.
    -   آخر عمليات الأتمتة والنسخ الاحتياطي والتنبيهات.
    -   مؤشرات واضحة للحالة: Healthy / Warning / Critical / Unknown.
    -   تحديث دوري للمعلومات دون إعادة تحميل الصفحة بالكامل عند الإمكان.
4.  servers
    -   تسجيل الخوادم وإدارتها.
    -   الاسم والوصف والبيئة (Production / Staging / Development).
    -   عنوان IP أو hostname ومنفذ SSH واسم المستخدم.
    -   نظام التشغيل وإصداره والمعمارية.
    -   حالة الاتصال وآخر فحص.
    -   تصنيف الخوادم والمجموعات.
    -   لا تخزن كلمات المرور أو مفاتيح SSH كنص واضح.
    -   دعم خادم محلي وخوادم بعيدة، مع عدم افتراض ثبات عنوان IP في
        الشبكات التي تستخدم DHCP.
5.  automation
    -   الربط مع Semaphore API.
    -   عرض Projects وTemplates وInventories وRepositories وTask Runs
        وفق ما تسمح به API والإصدار المثبت.
    -   تشغيل Template مع Parameters مسموح بها ومحددة مسبقاً.
    -   عرض رقم المهمة والحالة ووقت البدء والانتهاء والسجلات.
    -   إلغاء المهمة إذا كانت API تدعم ذلك وبحسب الصلاحيات.
    -   جدولة المهام من Semaphore أو تكامل مع جدولة معتمدة، دون إنشاء
        جدولة متضاربة.
    -   سجل كامل لكل طلب تشغيل صادر من Django.
    -   عدم عرض أسرار Semaphore أو Ansible Vault للمستخدمين غير
        المخولين.
    -   استخدام API version/documentation المطابقة للإصدار المثبت،
        والتحقق من endpoints فعلياً.
6.  docker_manager
    -   عرض Docker hosts.
    -   عرض Containers وحالاتها وصورها ومنافذها وشبكاتها وVolumes
        المرتبطة بها.
    -   عرض Docker Compose projects إن أمكن اكتشافها بصورة آمنة.
    -   Start / Stop / Restart للحاويات المعتمدة.
    -   عرض logs وresource usage.
    -   عرض حالة الصور والتحديثات المتاحة عند توفر مصدر موثوق.
    -   إدارة Compose عبر Playbooks/Templates معتمدة.
    -   عدم السماح بحذف Volume أو Container أو Image إلا بصلاحية عالية
        وتأكيد صريح.
    -   لا تعرض أوامر تنفيذ حرة للمستخدم العادي.
    -   لا تمنح Django وصولاً غير مقيد إلى Docker socket؛ لأن ذلك يعادل
        عملياً صلاحيات root على المضيف. فضّل التنفيذ عبر
        Semaphore/Ansible، أو وسيط محدود الصلاحيات ومحدد العمليات.
7.  odoo_manager
    -   إدارة نسخ Odoo المستضافة، ومنها Odoo 17 وOdoo 19، دون افتراض أن
        جميع النسخ تستخدم طريقة تثبيت واحدة.
    -   تسجيل كل Instance بشكل مستقل.
    -   الاسم والإصدار والبيئة والمضيف والمنفذ والنطاق.
    -   نوع التثبيت: Docker / Service / Other.
    -   مسار الإعدادات ومسار الإضافات ومسارات البيانات بعد التحقق منها.
    -   حالة الخدمة والحاويات وقاعدة البيانات.
    -   Start / Stop / Restart من خلال عمليات معتمدة.
    -   عرض logs وحالة HTTP وفحص الاتصال.
    -   معلومات قواعد البيانات المرتبطة دون كشف بيانات الدخول.
    -   متابعة مساحة filestore والنسخ الاحتياطية.
    -   عرض حالة تحديث الإضافات أو تنفيذ تحديثها فقط عبر Playbook معتمد
        وبعد نسخة احتياطية.
    -   دعم أكثر من قاعدة بيانات وأكثر من شركة دون خلط بيانات Instances.
    -   لا تنفذ upgrade أو restore أو حذف قاعدة بيانات مباشرة دون تأكيد
        وخطة استرجاع.
8.  django_projects
    -   تسجيل وإدارة مشاريع Django المتعددة.
    -   اسم المشروع والوصف والمضيف والبيئة والنطاق والمنفذ.
    -   طريقة التشغيل: Docker Compose أو systemd أو طريقة موثقة أخرى.
    -   Git repository والفرع وآخر commit عند توفر صلاحية الربط.
    -   حالة التطبيق وHTTP health check.
    -   حالة migrations والمهام الخلفية إن كانت معرفة.
    -   Start / Stop / Restart وDeploy من خلال Playbooks معتمدة.
    -   عرض logs وإصدارات التطبيق.
    -   إدارة متغيرات البيئة بصورة آمنة دون إظهار الأسرار.
    -   لا تنفذ git pull أو migration على Production دون مسار نشر معتمد
        ونسخة احتياطية عند الحاجة.
9.  databases
    -   دعم PostgreSQL وRedis في المرحلة الأولى.
    -   عرض Instances وقواعد البيانات والحالة والاتصال والاستخدام.
    -   عرض المساحة وعدد الاتصالات والمؤشرات المتاحة.
    -   فحص الاتصال وعمليات health check.
    -   إنشاء قواعد بيانات أو مستخدمين عبر Playbooks معتمدة وبصلاحيات
        محددة إذا أُضيفت هذه الميزة.
    -   لا تعرض كلمات المرور أو connection strings الحساسة.
    -   لا توفر حذفاً أو تعديلاً مباشراً خطيراً من الواجهة.
    -   لا تنفذ استعلامات SQL حرة من واجهة المستخدم.
10. backup
    -   سياسة نسخ احتياطي لكل خادم أو خدمة أو قاعدة بيانات.
    -   دعم PostgreSQL logical backups، ونسخ ملفات التطبيقات وOdoo
        filestore، وملفات Compose والإعدادات المطلوبة.
    -   تحديد الجدولة والاحتفاظ (Retention) ومكان التخزين.
    -   دعم نسخة محلية ووجهة خارجية آمنة عند إعدادها.
    -   تشفير النسخ الاحتياطية الحساسة وإدارة مفاتيح التشفير خارج
        المستودع.
    -   عرض وقت آخر نسخة وحجمها ونتيجتها.
    -   التحقق من سلامة النسخة checksum.
    -   تنفيذ Restore من خلال إجراء منفصل عالي الصلاحية، مع تأكيد مزدوج
        ونسخة أمان قبل الاستعادة.
    -   اختبار الاستعادة دورياً في بيئة غير إنتاجية؛ فالنسخة التي لم
        تُختبر استعادتها ليست ضماناً كافياً.
    -   عدم حذف النسخ القديمة قبل التأكد من سياسة الاحتفاظ ووجود نسخ
        سليمة بديلة.
    -   توفير سجل Audit لكل عملية Backup وRestore.
11. monitoring
    -   دمج Prometheus وNode Exporter لمقاييس الخادم.
    -   إمكانية دمج Grafana لعرض لوحات متقدمة.
    -   مراقبة CPU وRAM وDisk وNetwork وLoad Average.
    -   مراقبة Docker containers والخدمات الأساسية.
    -   مراقبة PostgreSQL وRedis عند توفر exporters أو health checks
        مناسبة.
    -   مراقبة HTTP endpoints لتطبيقات Odoo وDjango.
    -   تعريف thresholds قابلة للتعديل.
    -   عرض آخر تحديث للمقاييس ومصدرها.
    -   التعامل مع البيانات غير المتاحة كـ Unknown وليس Healthy.
    -   لا تجمع بيانات المراقبة من خلال تنفيذ أوامر متكررة ثقيلة على
        الخادم.
12. alerts
    -   تنبيهات عند توقف خدمة أو فشل فحص HTTP.
    -   تنبيه عند ارتفاع CPU أو RAM أو امتلاء القرص.
    -   تنبيه عند فشل النسخ الاحتياطي أو الأتمتة.
    -   تنبيه عند انقطاع الخادم.
    -   دعم البريد الإلكتروني، وإضافة Telegram أو قنوات أخرى اختيارياً.
    -   منع تكرار التنبيه المزعج باستخدام deduplication وcooldown.
    -   سجل للتنبيهات وحالاتها ووقت حلها.
13. network_domains
    -   عرض النطاقات والخدمات المرتبطة بها.
    -   إعدادات Reverse Proxy وTraefik عند اعتماده.
    -   متابعة حالة TLS/SSL وتاريخ انتهاء الشهادة.
    -   عرض قواعد التوجيه المعتمدة.
    -   لا تعدل DNS أو Firewall أو منافذ الإنتاج تلقائياً.
    -   تنفيذ أي تغيير شبكي عبر Playbook واضح مع مراجعة وتأكيد.
14. audit
    -   تسجيل المستخدم والوقت والإجراء والهدف والنتيجة.
    -   تسجيل عمليات الدخول والتغييرات الحساسة وتشغيل المهام وعمليات
        Docker والنسخ والاستعادة.
    -   حفظ correlation ID يربط طلب Django بمهمة Semaphore.
    -   منع المستخدم العادي من تعديل أو حذف سجلات التدقيق.
    -   عدم تسجيل كلمات المرور أو tokens أو المفاتيح أو محتوى الأسرار.

======================================================================
7. التكامل مع Ansible Semaphore
======================================================================

اجعل التكامل في تطبيق مستقل وطبقة Service/Client، مثلاً: -
SemaphoreClient: مسؤول عن HTTP requests والمصادقة. - SemaphoreService:
منطق الأعمال والتحقق من العمليات. - DTOs أو serializers داخلية لتوحيد
البيانات. - Webhook handler اختياري للتحقق من نتائج التنفيذ إذا كان
الإصدار يدعمه.

المتطلبات: 1. إعداد Base URL وToken من متغيرات بيئة أو Secret Store. 2.
استخدام HTTPS عند الاتصال عبر شبكة غير موثوقة. 3. ضبط connect/read
timeouts. 4. معالجة 401 و403 و404 و429 و5xx وأخطاء الشبكة. 5. عدم إعادة
إرسال عمليات غير idempotent تلقائياً دون تحقق. 6. دعم pagination إذا كانت
API تستخدمها. 7. تخزين معرفات المشاريع والقوالب والخوادم في قاعدة Django
مع إمكانية المزامنة. 8. لا تفترض أسماء endpoints أو شكل JSON؛ اقرأ توثيق
الإصدار المثبت واختبر الاستجابات. 9. لا تخزن token في قاعدة البيانات كنص
واضح. 10. استخدم أقل صلاحية ممكنة لحساب التكامل. 11. لا تعرض زر تشغيل
إلا إذا كان المستخدم مخولاً وكان Template معتمداً. 12. مرر Parameters
محددة ومتحققاً منها فقط، ولا تسمح بحقن أوامر Shell أو تغيير Inventory
بشكل غير مصرح. 13. خزّن رقم المهمة الخارجي وحالتها وسجلاتها المختصرة
ورابطها إن توفر. 14. اجعل Django قادراً على متابعة حالة المهمة دون إبقاء
HTTP request مفتوحاً. 15. وفر صفحة إعداد اتصال مع زر Test Connection دون
كشف بيانات الاعتماد.

تدفق التشغيل: - المستخدم يطلب إجراءً من Django. - Django يتحقق من
المستخدم والدور والخادم والبيئة والمدخلات. - Django ينشئ Audit Event
وOperation Request. - Django يرسل طلب تشغيل Template معتمد إلى
Semaphore. - Semaphore يشغل Ansible على الهدف المحدد. - Django يحفظ
external task ID. - مهمة polling أو webhook تحدث حالة التنفيذ. - تعرض
الواجهة الحالة والسجلات والنتيجة. - عند الفشل، تعرض رسالة مفهومة ومرجع
السجل، دون كشف أسرار.

8. تنظيم Ansible Project
======================================================================

أنشئ أو أعد تنظيم مجلد Ansible بشكل واضح، مع الحفاظ على Playbooks
الحالية بعد فحصها. هيكل مقترح:

ansible-project/ ansible.cfg inventories/ development/ staging/
production/ playbooks/ server_info.yml docker/ odoo/ odoo17.yml
odoo19.yml django/ postgresql/ redis/ backup/ monitoring/ traefik/
maintenance/ roles/ common/ system_info/ docker/ odoo/ django/
postgresql/ redis/ backup/ monitoring/ traefik/ group_vars/ host_vars/
files/ templates/ requirements.yml README.md

قواعد Ansible: - استخدم Roles قابلة لإعادة الاستخدام. - استخدم Ansible
Vault أو Secret Manager للأسرار. - لا تضع كلمات المرور في Git أو
Inventory كنص واضح. - استخدم become فقط عند الحاجة. - حدد hosts
وenvironment بوضوح. - استخدم tags لتقسيم العمليات. - اجعل المهام
idempotent قدر الإمكان. - أضف pre_tasks للتحقق من الشروط والمضيف
المستهدف. - استخدم handlers لإعادة تشغيل الخدمات عند تغير الإعدادات
فقط. - استخدم check mode وdiff حيثما أمكن. - لا تستخدم shell أو command
إذا كانت هناك Ansible module مناسبة. - لا تستخدم wildcard hosts في مهام
خطرة. - أضف confirmation gate للعمليات الخطرة. - أضف README لكل Playbook
يشرح الغرض والمتطلبات والآثار وطريقة التراجع. - افصل Development
وStaging وProduction في Inventories. - لا تجعل تشغيل Playbook على
Production هو الاختيار الافتراضي.

راجع Playbooks الحالية مثل: - server_info.yml - odoo17.yml -
odoo19.yml - django.yml - docker.yml إن كان موجوداً أو مطلوباً إنشاؤه.

لا تعدّلها قبل قراءة محتواها والتحقق من أهدافها ومخرجاتها.

14. الأمن والحماية
======================================================================

الأمن شرط أساسي وليس مرحلة تجميلية.

-   استخدم HTTPS في الإنتاج.
-   استخدم Django security settings المناسبة للإنتاج.
-   فعّل CSRF وقيود الجلسات والكوكيز الآمنة.
-   طبّق حماية من brute force وrate limiting.
-   استخدم RBAC وصلاحيات على مستوى الخادم والبيئة والعملية.
-   افصل أدوار Viewer وOperator وAdministrator وSecurity/Audit إن لزم.
-   العمليات الخطرة تحتاج صلاحيات خاصة وتأكيداً صريحاً.
-   لا تعرض أو تسجل passwords أو tokens أو private keys أو secrets.
-   استخدم environment variables أو Secret Manager.
-   لا تضع .env الحقيقي في Git.
-   أضف .env.example بقيم توضيحية غير حقيقية.
-   اضبط صلاحيات ملفات الأسرار.
-   تحقق من مدخلات المستخدم في Backend.
-   امنع command injection وpath traversal وSSRF.
-   لا تسمح للمستخدم بإرسال URL داخلي عشوائي ليتم فحصه من الخادم.
-   قيّد عناوين ووجهات الاتصال المسموح بها.
-   استخدم timeouts وحدوداً لحجم السجلات والطلبات.
-   لا تعرض تفاصيل stack trace للمستخدم في Production.
-   أضف Security Audit للأحداث الحساسة.
-   افصل حساب تشغيل Django عن root.
-   لا تمنح حساب Django عضوية غير مقيدة في docker group.
-   لا تفتح Docker socket على شبكة عامة.
-   استخدم SSH keys محددة الصلاحيات، ويفضل حسابات Ansible مخصصة.
-   قيّد الوصول إلى Semaphore وPrometheus وGrafana وقواعد البيانات.
-   ضع Firewall rules بمراجعة بشرية قبل التعديل.
-   لا تنفذ أوامر تدميرية أو تغييرات على Production دون موافقة صريحة.

افصل بين: - طلب المستخدم. - مهمة Django الخلفية. - Semaphore Task. -
نتيجة Ansible.

20. مراحل التنفيذ المطلوبة

نفّذ المشروع على المراحل التالية، ولا تنتقل إلى مرحلة عالية المخاطر قبل
نجاح المرحلة السابقة:

المرحلة 3: Server Management - إضافة الخوادم والمجموعات والبيئات. - فحص

المرحلة 4: Docker Management - اكتشاف Docker hosts. - عرض

المرحلة 5: Odoo Management - تسجيل Odoo 17 وOdoo 19. - اكتشاف طريقة
تشغيل كل نسخة. - عرض الحالة والسجلات. - Restart وHealth Check. - Backup
database وfilestore. - عمليات الصيانة والتحديث بضوابط.

المرحلة 6: Django Projects Management - تسجيل المشاريع. - فحص HTTP. -
عرض حالة التشغيل والإصدار. - Deploy workflow معتمد. - Backup وRollback
حيثما أمكن.

المرحلة 7: Databases - PostgreSQL monitoring. - Redis monitoring. - فحص
الاتصال والمساحة والاتصالات. - إجراءات الإدارة المسموحة عبر Playbooks.

المرحلة 8: Backup & Restore - السياسات والجدولة. - النسخ المحلية
والخارجية. - التحقق من السلامة. - إجراءات الاستعادة الآمنة. - اختبار
الاستعادة.

المرحلة 9: Monitoring & Alerts - Prometheus وNode Exporter. - Grafana
اختيارياً. - مؤشرات الخادم والخدمات. - التنبيهات وسجلها. - منع التكرار.

المرحلة 10: Domains & Traefik - عرض النطاقات والخدمات. - متابعة TLS. -

المرحلة 11: Hardening & Production Readiness - مراجعة أمنية. - مراجعة

======================================================================
21. قواعد العمل مع مساعد البرمجة AI
======================================================================

عند تنفيذ هذا البرومبت: 1. لا تكتفِ بكتابة خطة؛ بعد دراسة المشروع ابدأ
تنفيذ التغييرات المعتمدة فعلياً. 2. لا تنشئ كل الوحدات دفعة واحدة بصورة
سطحية. 3. نفّذ كل مرحلة على حدة. 4. قبل تعديل أي ملف، افهم وظيفته
واعتمادياته. 5. لا تستبدل ملفات كاملة إذا كان تعديل محدود كافياً. 6. لا
تحذف وظائف موجودة دون مبرر وموافقة. 7. لا تنشئ بيانات تجريبية في بيئة
Production. 8. لا تستخدم Mock data في الواجهة النهائية لإظهار أن التكامل
يعمل. 9. عند عدم توفر خدمة خارجية، أنشئ واجهة واضحة لحالة Not Configured
ولا تدّعِ نجاح الاتصال. 10. لا تخترع Semaphore API endpoints؛ تحقق من
الوثائق والإصدار الفعلي. 11. لا تفترض أسماء الحاويات أو المنافذ أو
مسارات الملفات؛ اكتشفها أو اطلب تأكيدها. 12. لا تشغّل أوامر قد توقف Odoo
أو PostgreSQL أو Docker أو الشبكة دون موافقة. 13. خذ نسخة احتياطية من
الملفات وقاعدة البيانات قبل تغييرات البنية الحساسة. 14. استخدم
migrations آمنة وقابلة للمراجعة. 15. شغّل formatter وlint وtests بعد كل
مرحلة. 16. أصلح الأخطاء الناتجة عن التغييرات قبل الانتقال. 17. لا تترك
TODO أو صفحات شكلية مكان وظائف مطلوبة دون توضيح. 18. اذكر بوضوح ما اكتمل
وما لم يكتمل وما يحتاج بيانات أو صلاحيات. 19. وثق كل متغير بيئة جديد وكل
Playbook جديد وكل إجراء تشغيلي. 20. عند الحاجة إلى قرار يؤثر على
Production أو الأمن أو البيانات، توقف واطلب موافقة المستخدم.

في نهاية كل مرحلة قدم تقريراً يحتوي على: - ما الذي تم تنفيذه. - الملفات
التي أُنشئت أو عُدلت. - قاعدة البيانات وmigrations. - الاختبارات
ونتائجها. - التكاملات التي تم التحقق منها. - المخاطر أو القيود
المتبقية. - طريقة تشغيل وتجربة الوظيفة. - الخطوة التالية المقترحة.

======================================================================
22. المطلوب النهائي
======================================================================

أريد منصة Infrastructure Manager عملية واحترافية، وليست مجرد Dashboard
شكلية.

يجب أن توفر: - واجهة Django مركزية. - تكاملاً حقيقياً وآمناً مع Semaphore
API. - استخدام Ansible Playbooks لإدارة الخوادم والخدمات. - إدارة
Docker. - إدارة Odoo 17 وOdoo 19. - إدارة مشاريع Django المتعددة. -
مراقبة PostgreSQL وRedis. - مراقبة CPU وRAM وDisk وNetwork. - النسخ
الاحتياطي والاستعادة. - إدارة Traefik والنطاقات وشهادات SSL. - التنبيهات
والسجلات والتدقيق. - مستخدمين وأدواراً وصلاحيات دقيقة. - دعم العربية
والإنجليزية. - بنية قابلة لإضافة خوادم وخدمات جديدة مستقبلاً.

ابدأ الآن بالمرحلة 0 فقط: افحص المشروع الحالي وبيئة التشغيل، ثم قدم
تقرير Discovery وخطة تنفيذ مبنية على الموجود فعلياً. لا تنفذ تغييرات خطرة
أو تدميرية في مرحلة الفحص. بعد ذلك ابدأ المرحلة الأولى تدريجياً، مع
الحفاظ على الخدمات والبيانات الحالية.
