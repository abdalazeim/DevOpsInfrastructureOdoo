# بنية Django Enterprise Starter

القالب تطبيق Django معياري (Modular Monolith). يحتفظ بالوحدات داخل مشروع واحد،
ويفصل مسؤوليات الحسابات والنواة ووحدات المجال من دون فرض توزيع الخدمات.

```text
config/settings/      إعدادات الأساس والتطوير والاختبار والإنتاج وسطح المكتب
apps/core/            الاستجابات، الترقيم، التدقيق، الإعدادات، الصلاحيات المشتركة
apps/accounts/        المستخدمون والأدوار والمجموعات والمصادقة
apps/modules/example/ وحدة CRUD مرجعية عامة تعمل افتراضيًا
examples/             وحدات مجال اختيارية لا تحملها الإعدادات الافتراضية
templates/             واجهة الويب وقوالب الصفحات
static/                CSS وJavaScript والأصول الثابتة
tests/                 اختبارات التكامل والعقد
deployment/            ملفات Docker وNginx وGunicorn والنشر
```

## تدفق طلب API

`config/urls.py` يركّب المسارات ذات الإصدار من `config/api_urls.py`. المصادقة
تمر عبر SimpleJWT، ثم تتحقق كل وحدة من صلاحيات المستخدم. الخدمات تتحقق من
مدخلات الوحدة وتستعمل المستودعات لعمليات البيانات. ترجع الأدوات المشتركة غلافًا
موحّدًا وتفاصيل ترقيم ثابتة.

## إضافة وحدة

أنشئ وحدة باستخدام `python manage.py startmodule <name> --label "<label>"`،
ثم سجّل تطبيقها ومساراتها وصلاحياتها صراحةً. يبدأ المثال المرجعي في
`apps/modules/example`؛ اتبع `development/ADDING_MODULE.md`.

## إعدادات التشغيل

يوضع الإعداد المشترك في `config/settings/base.py`، وتستورد البيئات الفرعية
الأساس ثم تضبط ما يخص التشغيل فقط. يجب أن يستخدم الإنتاج `production.py`؛ أما
SQLite و`development.py` فمخصصان للتطوير.

## مواصفة الوحدة 1: سجل الخوادم والبنية التحتية

### 1. الغرض

توفير مصدر موحد وموثوق لهوية الخوادم المُدارة وبيانات اتصالها ومجموعاتها
ووسومها وخدماتها، مع التقاط لقطات Linux حقيقية محلية أو عبر SSH، وإتاحة
العمليات المسجلة والمصرح بها من خلال لوحة الويب وREST API. لا تحتفظ الوحدات
الأخرى بنسخ مستقلة من بيانات الخادم؛ بل تربط مواردها بـ`ManagedHost`.

### 2. المكونات الداخلية

- نماذج المجال: `ManagedHost`, `ServerGroup`, `ServerTag`, `ManagedService`,
  `InfrastructureSnapshot`, `InfrastructureSyncRecord`.
- محول الاتصال SSH ذي التحقق من مفاتيح المضيف، ومحول Linux المحلي للقراءة.
- خدمة الاكتشاف التي تحفظ اللقطة وتحدّث حقول النظام المرصودة دون الكتابة فوق
  إعدادات الاتصال والبيانات الإدارية.
- بوابة العمليات المسجلة `InfrastructureEngine` وسياسة `ExecutionPolicy`.
- خدمات الجرد والعرض عبر تطبيق `apps.infrastructure` وواجهة لوحة التحكم.
- REST API بإصدار `/api/v1/servers/` وغلاف الاستجابة المشترك.

### 3. النماذج والحقول

- `ManagedHost` (موجود): الاسم، hostname، النوع والبيئة، نوع الاتصال والمنفذ،
  مرجع `Credential`، بيانات النظام، الموقع، حد Ansible، هوية Prometheus،
  التفعيل/محلية الخادم، حالة الاتصال وتواريخ التحقق. تبقى بياناته اليدوية
  منفصلة عن البيانات المرصودة.
- `ServerGroup` (موجود): اسم فريد ووصف.
- `ServerTag` (يضاف): اسم فريد واسم عرض/لون اختياريان وتاريخ الإنشاء.
- علاقة متعدد-إلى-متعدد بين `ManagedHost` وكل من `ServerGroup` و`ServerTag`.
- `ManagedService` (موجود): الخدمة مرتبطة بخادم واحد، مع نوعها ومعلومات
  الحاويات/Compose وفحص الصحة الاختياري.
- `InfrastructureSnapshot` (موجود): أحدث لقطة واحدة لكل خادم، مصدرها وحالتها
  وبيانات JSON وتوفر الأقسام ومدة الجمع والخطأ المنقح.
- `InfrastructureSyncRecord` (يضاف): سجل دائم لكل محاولة مزامنة؛ UUID، الخادم،
  المصدر والحالة، ملخص الأقسام المحدثة والأخطاء المنقحة والمدة ووقت البدء
  والانتهاء. تبقى اللقطة الحالية للقراءة السريعة ولا تحل محل سجل التاريخ.

### 4. علاقات قاعدة البيانات

- الخادم له مجموعات ووسوم متعددة، وخدمات متعددة، وبيانات اعتماد اختيارية
  محمية بـ`PROTECT`، ولقطة حالية واحدة، وسجلات مزامنة متعددة.
- الموارد التشغيلية التابعة (المهام، الخدمات، قواعد التنبيه، قواعد البيانات،
  الأتمتة والنسخ الاحتياطي) تشير إلى الخادم عبر FK بدل تكرار عنوانه.
- حذف الخادم لا يحذف سجل التدقيق أو المهام المنفذة؛ قيود الحذف الحالية للموارد
  المرتبطة تُحترم، ويمنع حذف الخادم ذي الخدمات المرتبطة.
- يفرض قيد قاعدة البيانات وجود خادم محلي واحد كحد أقصى، وفريدة اسم المجموعة
  والوسم واسم الخادم، وفهارس لحالة الاتصال والبيئة وتواريخ المزامنة.

### 5. الخدمات ومنطق المجال

- إنشاء/تعديل الجرد يتحقق من اتساق المحلي وSSH، ويمنع تخزين سر في حقول الخادم.
- ربط بيانات الاعتماد لا يكشف السر؛ مفاتيح SSH المضيف يجب أن تكون موثوقة مسبقًا.
- الاكتشاف يجمع أقسام النظام والمعالج والذاكرة والتخزين والشبكة وDNS والخدمات
  والعمليات ومؤشرات توفر الأدوات. يميز `unavailable` و`unsupported` عن قيمة صفر.
- تحفظ كل محاولة مزامنة كسجل، وتبقى بيانات الإدارة اليدوية دون استبدال آلي.
- اختبار الاتصال والاكتشاف المباشر هما عمليات قراءة ثابتة؛ إعادة تشغيل systemd
  عملية تغيير مسجلة، تتطلب صلاحية وتأكيدًا وإرسالًا عبر مدير المهام.
- كل تغيير حساس يسجل عبر خدمة التدقيق؛ لا تسجل كلمات مرور أو مفاتيح أو محتوى
  أسرار.

### 6. API والواجهات

العقد الإضافي تحت `/api/v1/servers/` (مع إبقاء المسارات القديمة):

- `GET /` قائمة مرقمة مع مرشحات `q`, `environment`, `connection_status`,
  `group`, `tag`؛ و`POST /` لإنشاء خادم بصلاحية `server.create`.
- `GET /{id}/` للتفاصيل واللقطة الحالية؛ و`PATCH /{id}/` لتعديل الجرد
  بصلاحية `server.update`.
- `GET /groups/`, `POST /groups/`, `GET /tags/`, `POST /tags/` لإدارة
  تصنيفات الخوادم، مع صلاحيات العرض/الإدارة المناسبة.
- `GET /{id}/sync-history/` لتاريخ المزامنة.
- `POST /{id}/test-connection/` و`POST /{id}/discover/` لطلب العمليات؛
  ترجعان task id وحالة الإرسال ولا تنفذان عملاً بعيدًا طويلًا ضمن طلب HTTP.
- تعاد كل النتائج بغلاف Core الموحد، وتظل تفاصيل الأسرار مستبعدة.
- تتكامل صفحة Dashboard → Inventory مع حقول الوسوم/المجموعات وسجل/حالة
  الاكتشاف؛ وتظل أزرار العمليات معطلة/مفسرة عندما يكون dispatcher غير جاهز.

### 7. الصلاحيات

- `infrastructure_view` / `server.view`: عرض الخوادم واللقطات والتاريخ.
- `server.create`, `server.update`, `server.delete`: تغييرات سجل الخوادم.
- `server.connect`: اختبار اتصال SSH.
- `server.discover`: اكتشاف النظام.
- `infrastructure_manage`: توافق للخلف وإدارة الخدمات/المجموعات عند الحاجة.
- `linux.service.restart`: عملية تغيير systemd، مع تأكيد صريح وصلاحية مستقلة.
- تطبق الصلاحيات في لوحة الويب وAPI ومحرك التنفيذ والعامل؛ صلاحية إدارة الخادم
  لا تعني تلقائيًا صلاحية كشف الأسرار أو تنفيذ عمليات نظام.

### 8. المهام الخلفية

- الاختبار والاكتشاف يمكن تشغيلهما مباشرة فقط كمسارات قراءة محدودة ومدروسة،
  وتتوفر واجهة dispatch لاستخدام Celery عند تمكين Redis والعامل.
- كل تغيير نظام (مثل restart) يتطلب dispatcher جاهزًا؛ لا يوجد fallback متزامن.
- يحفظ `Task` الحالة والسجل، ويعاد التحقق من الحساب والسياسة عند التنفيذ.
- لا يدخل أي أمر مستخدم حر إلى طابور التنفيذ. لا يشغل SQLite دور ناقل المهام.

### 9. محولات البنية التحتية

- Linux محلي: `psutil` وواجهات النظام؛ `systemctl` لاستعلام قائمة الخدمات.
- Linux بعيد: Paramiko مع `RejectPolicy` وknown_hosts، وSFTP/أوامر قراءة ثابتة
  محدودة الزمن والحجم؛ لا يقبل المحول أوامر من المستخدم.
- systemd: `systemctl` محلي فقط، وحدات خدمة من قائمة حديثة معروفة، وتحقق بعد
  إعادة التشغيل.
- Docker وAnsible وFirewall لها نقاط تكامل/وحدات مجاورة، لكنها ليست ضمن نطاق
  CRUD هذه الوحدة أو عملياتها في هذه المرحلة.

### 10. الأحداث والإشعارات

- يسجل كل اكتشاف كمحاولة `InfrastructureSyncRecord` ويحدث حالة الاتصال بعد
  نتيجة المحول فقط.
- تسجل تغييرات الخادم واختبار الاتصال والعمليات في `AuditLog`.
- نتائج الانقطاع والتنبيه يستهلكها Monitoring؛ لا تنشئ هذه الوحدة نظام تنبيه
  موازيًا ولا ترسل إشعارًا غير موصول بقناة Notifications.
- لا تُنفّذ إشعارات مباشرة داخل معاملة اكتشاف طويلة.

### 11. الاعتماديات على الوحدات

- تعتمد على Core للتدقيق والاستجابات والإعدادات؛ Accounts للصلاحيات؛ Security
  لتشفير بيانات اعتماد SSH؛ Tasks لإرسال العمليات وحفظ نتائجها؛ Dashboard
  للواجهة وتجميع البيانات.
- Monitoring يقرأ هوية الخادم ولقطاته؛ Automation يستخدم الخادم كهدف وقيد
  Ansible؛ Databases وBackup وContainers تربط أصولها بـ`ManagedHost`.
- لا تعتمد على Docker أو Ansible لتنفيذ اكتشاف Linux الأساسي.

### 12. اختبارات القبول

- ترحيلات SQLite قابلة للتطبيق و`makemigrations --check` نظيف.
- قيود المحلية/الأسماء وعلاقات المجموعة والوسم والخدمات والاعتمادات سليمة.
- إنشاء وعرض/تعديل الخادم عبر API يتطلب المصادقة والصلاحية المحددة؛ لا تتسرب
  بيانات الاعتماد أو قيمها المشفرة في أي استجابة.
- اختبار الاتصال والاكتشاف يرفضان مستخدمًا بلا صلاحية، ويعيدان حالة خطأ
  مناسبة دون كشف أسرار؛ الاكتشاف الوهمي يُختبر بمحول mock.
- كل محاولة اكتشاف تنتج سجل مزامنة؛ تحديث الرصد لا يكتب فوق الوصف أو البيئة أو
  بيانات الاعتماد.
- API القائمة يدعم المرشحات والترقيم، وتاريخ المزامنة يعرض سجلات الخادم نفسه.
- صفحة الجرد تعرض المجموعات والوسوم والحالة واللقطة وتبقي روابط المهام والخدمات.
- اختبارات العلاقات تتحقق من FK مع المهام والخدمات والتنبيهات وقواعد بيانات/
  نسخ احتياطي ذات صلة، دون تكرار بيانات الخادم.
- اختبارات وحدة للمحولات، وAPI وصلاحيات، واختبار واجهة/قالب، ثم كامل مجموعة
  الاختبارات وفحص Django.

### حدود هذه المرحلة

هذه الوحدة توحد السجل والاكتشاف والاتصال والعمليات الآمنة الموجودة وتكمل
واجهتها وعلاقاتها. لا تدعي بعد إدارة الحزم أو المستخدمين المحليين أو الجدار
الناري أو تعديل إعدادات الشبكة أو إنهاء العمليات؛ هذه عمليات عالية الأثر تحتاج
مواصفات وسياسات واختبارات مستقلة قبل تنفيذها كوحدة لاحقة.

## مواصفة تنفيذ المرحلة 2: اكتشاف Linux المحلي

هذه مواصفة تنفيذ للمرحلة المحلية الواردة في المرفق المحدّث. لا توسع المرحلة
إلى SSH (المرحلة 3)، ولا تنفذ تعديلًا للنظام أو تغييرات Docker/Ansible.

**حالة القبول:** منفذة ومتحقق منها. لا تتطلب جداول أو ترحيلات جديدة؛ طُبقت
الترحيلات الحالية بنجاح. اجتازت فحوصات Django و`makemigrations --check` وجميع
اختبارات المشروع (80 اختبارًا)، بما فيها جامع Linux وواجهة Inventory وREST
API والصلاحيات وحداثة اللقطة وعلاقات السجل.

### 1. الغرض

رفع اكتشاف الخادم المحلي المسجل إلى لقطة تشغيل مفصلة فعلية؛ رصد نظام التشغيل
والعتاد والموارد والتخزين والشبكة والخدمات والعمليات ومؤشرات التوفر، مع حفظ
مصدر القياس ووقته وحالة كل قسم، وتمييز الصفر عن غير المتاح أو غير المدعوم.

### 2. المكونات الداخلية

- `infrastructure_engine.adapters.linux.local`: جامع محلي للقراءة فقط، بأقسام
  مستقلة ومعالجات مساعدة قابلة للاختبار.
- `apps.infrastructure.services.discovery`: حفظ اللقطة وسجل المحاولة وتحديث
  حقول النظام المرصودة بأمان.
- `InfrastructureSnapshot` و`InfrastructureSyncRecord`: التخزين الحالي
  والتاريخي الموجودان من مرحلة سجل الخوادم.
- محرك العمليات ولوحة Inventory/API الحاليةان لطلب الاكتشاف وعرض النتيجة.
- لا نموذج جديد ولا اعتماد Python جديد مطلوبان في هذه المرحلة.

### 3. نماذج وحقول البيانات

لا تضاف جداول جديدة. توسع بيانات `InfrastructureSnapshot.data` المحفوظة في
JSON إلى الأقسام التالية:

- `system`: hostname، النظام والتوزيعة وإصدارها، kernel، architecture، وقت
  الإقلاع وuptime، timezone وlocale.
- `cpu`: model، architecture، الأنوية الفيزيائية والمنطقية، التردد إن توفر،
  الاستخدام الإجمالي ولكل نواة، load average.
- `memory`: total/used/available، cached/buffers إن توفر، ونظير swap.
- `storage`: كائن يحوي devices وfilesystems/mounts والسعة والاستخدام ونوع
  filesystem وقراءات/كتابات I/O حين يدعم النظام ذلك. يبقى `disks` قائمة
  filesystems توافقية للعملاء الذين استهلكوا شكل اللقطة السابق.
- `network_interfaces.items`: الاسم والحالة والعناوين IPv4/IPv6 وعنوان MAC
  وإحصاءات الواجهة؛ `network_routes`: المسارات والبوابة الافتراضية؛ `dns`:
  خوادم DNS؛
  `network_connections`: المنافذ المستمعة والاتصالات التي يسمح النظام برؤيتها.
- `services`: وحدات systemd العاملة؛ `processes`: عينة محدودة مرتبة بالاستهلاك
  ولا تتضمن سطر الأوامر أو الملفات المفتوحة.
- `providers`: وجود أدوات Docker وAnsible وAPT/dpkg وsystemctl وsmartctl، وحالة
  Docker الفعلية فقط عبر فحص قراءة ثابت إن كانت الأداة متاحة.
- `system_security`: هوية/امتياز عملية التطبيق وحالة توافر أداة UFW فقط؛ لا قواعد
  جدار ناري أو مفاتيح أو محتوى ملفات إعداد حساسة في هذه المرحلة.

يبقى `availability` سجلًا موازيًا لكل قسم بقيم `available`, `unavailable`,
`unsupported` وسبب آمن، ويحتوي كل قسم متاح على `observed_at`. النتيجة العامة
`success` إذا اكتملت الأقسام، و`partial` إذا تعذر قسم، و`failed` فقط إذا لم
تنتج عملية الجمع أي بيانات مفيدة. القيم المفقودة `null` أو قوائم خالية مع حالة
توضح معناها؛ لا تتحول إلى صفر اصطناعي.

### 4. العلاقات

تظل اللقطة وسجل المحاولة مربوطين بالخادم المركزي `ManagedHost`. جميع عناصر
القياس محلية لهذا المورد؛ لا تنشئ المرحلة نسخًا منفصلة من الأجهزة أو الشبكات
ولا تغير علاقات Modules الأخرى.

### 5. الخدمات والمنطق

- كل قسم جامع مستقل؛ إخفاقه لا يمنع حفظ الأقسام الناجحة.
- جميع أوامر النظام ثابتة بلا بيانات مستخدم، عبر `subprocess` بقائمة argv
  مهلة قصيرة وقراءة stdout محدودة وبيئة محكومة؛ لا shell ولا أوامر متغيرة.
- استخدام psutil و`/proc` و`/sys` للقياسات، وsystemctl للاستعلام، وأدوات قراءة
  ثابتة فقط عند الحاجة.
- البيانات الوصفية اليدوية في `ManagedHost` (الوصف، البيئة، الموقع،
  الاعتمادات) لا تستبدل بنتيجة المسح.
- لا يتطلب المسح صلاحيات root؛ القسم الذي يحتاج صلاحية غير متاحة يعرض
  unavailable أو unsupported.
- لا يجمع process command lines أو أسرارًا، ويحد عدد الأجهزة/الاتصالات/
  العمليات وحجم النتائج.

### 6. API والواجهة

- لا تضاف واجهات مستقلة عن الموجودة: `POST /api/v1/servers/{id}/discover/`
  يرسل للمهمة المركزية عند تفعيل dispatch؛ والواجهة الحالية تحدث المحلي مباشرة
  كعملية قراءة محدودة.
- `GET /api/v1/servers/{id}/` يعيد لقطة الاكتشاف وavailability من الخادم
  نفسه؛ `GET /{id}/sync-history/` يعيد سجل الجمع.
- تعرض Inventory حقول الموارد كمعلومات snapshot واضحة مع حالات القسم والعمر؛
  لا تعرض `stale` على أنه current، ولا تفسر البيانات الغائبة على أنها صفر.
- لا يقدم هذا الجزء تبويبات إدارة أو أزرار تغيير نظام.

### 7. الصلاحيات

- القراءة والعرض: `server.view` أو صلاحية العرض القديمة.
- الاكتشاف: `server.discover`؛ ويمكن للواجهة القديمة المحافظة على alias العرض
  للتوافق.
- API إرسال مهمة الاكتشاف يتطلب أيضًا `task.view` أو `tasks_manage`.
- لا تغير المرحلة صلاحيات عمليات تغيير النظام.

### 8. المهام الخلفية

المسح اليدوي المتزامن الحالي محدود بمهل كل جامع؛ إرسال المسح عن بعد/المجدول
يبقى عبر Task Dispatcher عندما يكون جاهزًا. لا Redis/Celery جديدان ولا جدولة
ضمن هذا النطاق، ولا fallback متزامن لمسار API غير المتزامن.

### 9. المحولات

- Local Linux adapter باستخدام psutil وواجهات Linux الثابتة.
- systemd read-only عبر `systemctl list-units`.
- أدوات قراءة النظام `ip`, `lsblk`, `docker`, `ansible`, `apt-get`, `dpkg`,
  `smartctl` اختيارية؛ غيابها يسجل كتوافر غير مدعوم لا كفشل كامل.
- لا SSH أو Docker lifecycle أو Ansible execution في المرحلة المحلية.

### 10. الأحداث والتدقيق

كل محاولة تحدث `InfrastructureSyncRecord` ولقطة الحالية بشكل متسق. طلب
الاكتشاف يسجل في `AuditLog` عبر محرك العمليات. لا يصدر النظام إشعارًا مستقلًا؛
أي تنبيه عدم توفر يظل اختصاص Monitoring.

### 11. الاعتماديات

تعتمد على Core (التدقيق/التخزين/الوقت)، Infrastructure (الخادم/اللقطات)،
Dashboard (العرض)، وTasks لمسار API غير المتزامن فقط. لا تعتمد على Redis أو
Docker SDK أو Ansible لتجميع القياسات المحلية الأساسية.

### 12. اختبارات القبول

- تغطية مصادر كل قسم عبر mocks دون الاتصال بخوادم أو تشغيل تغييرات حقيقية.
- التحقق من cpu/memory/storage/network/system/services/processes/providers
  والحقول المتاحة وصيغها وحدود أحجامها.
- حالات أداة غائبة، صلاحية نظام ناقصة، بيانات معطوبة، timeout، وقسم واحد
  فاشل لا يسقط بقية اللقطة.
- التأكد أن الأوامر تستخدم argv ثابتًا، timeout، ولا تستخدم `shell=True` أو
  مدخلات HTTP.
- عدم إدراج command line للعمليات أو أسرار، وعدم إظهار صفر مزيف للمقاييس
  unavailable.
- الحفاظ على شكل `disks` التوافقي، وإبقاء filesystem measurements متاحة عند
  فشل أداة `lsblk` الاختيارية أو فساد مخرجاتها.
- حفظ لقطة وتاريخ ومحافظة على البيانات اليدوية، ودقة حالة freshness في UI/API.
- تطبيق الترحيلات (دون إنشاء ترحيل جديد متوقع)، فحص Django، واختبار REST/
  صلاحيات/قالب، ثم مجموعة الاختبارات الكاملة.

### حدود القبول

تثبت هذه المرحلة جمع معلومات محلية آمنًا، لا إدارة النظام. لا إدارة حزم أو
جدار ناري أو خدمات/عمليات تغييرية ولا restart/shutdown/reboot ولا فحص SMART
فعلي أو Docker API متكامل. تلك قدرات تتطلب مراحل وسياسات منفصلة.

## مواصفة تنفيذ المرحلة 3: محرك العمليات ومدير المهام

تستكمل هذه المرحلة بوابة تنفيذ العمليات المسجلة وتوفر REST API لمركز المهام.
تظل عمليات النظام خارج طلبات HTTP، وتبقى مهام قاعدة البيانات هي مصدر الحالة
والسجلات. إرسال المهام عبر Celery/Redis اختياري ومغلق افتراضيًا.

### 1. الغرض

- توحيد تنفيذ العمليات المصرح بها عبر `InfrastructureEngine` ذي عقود ومدخلات
  محددة.
- توفير سجل دائم ومرئي للطلبات والنتائج ومحاولات التنفيذ وسجلاتها.
- إتاحة عرض المهام وتفاصيلها وإلغاء/إعادة محاولة المهام المسموح بها عبر
  واجهات الويب وREST.
- منع تنفيذ عمليات النظام أو التراجع إلى تنفيذ متزامن عند غياب طابور المهام.

### 2. المكونات الداخلية

- سجل `OperationSpec` ومحرك التحقق والتفويض والتدقيق في
  `infrastructure_engine.core.engine`.
- سياسات التنفيذ والتحقق من المعاملات في
  `infrastructure_engine.security`.
- نماذج المهام وخدمات الانتقالات والسجلات والتنقيح في `apps.tasks`.
- Dispatcher اختياري لنشر UUID المهمة إلى Celery/Redis، وعامل يعيد التحقق من
  المستخدم والسياسة والهدف عبر المحرك.
- Task Center في لوحة Dashboard، وواجهات REST في `apps.tasks.api_views`.

### 3. النماذج والحقول

- لا تضاف جداول في النطاق الحالي. يحتفظ `Task` بـUUID، اسم/رمز عملية، المصدر،
  خادم الهدف، المستخدم، الأولوية والحالة، الملخص/الخطأ المنقح، بيانات آمنة،
  عدد المحاولات وحدها، والأوقات ووقت طلب الإلغاء.
- يحتفظ `TaskLog` بتسلسل فريد داخل المهمة، القناة، المحتوى المنقح والمحدود
  والطابع الزمني.
- تظل نتائج Celery غير معتمدة؛ ORM في Django هو المصدر الدائم للحالة والسجل.

### 4. العلاقات

- `Task.target_server` مرجع اختياري إلى `ManagedHost`؛
  `Task.requested_by` مرجع إلى المستخدم مع `SET_NULL`.
- `TaskLog` تابع للمهمة ويحذف معها.
- تربط حقول المصدر المهمة بسجل المجال الأصلي دون نسخ بياناته.

### 5. الخدمات والمنطق

- قائمة مسموح بها من عمليات Typed فقط؛ لا shell أوامر أو أسماء برامج أو
  معاملات حرّة من المستخدم.
- يجب التحقق من الحساب النشط، الصلاحية، الهدف، المعاملات، التأكيد وسياسة
  التنفيذ عند الطلب، ثم إعادة التحقق قبل التنفيذ الفعلي.
- تفرض آلة الحالة الانتقالات القانونية وحد المحاولات؛ الإرسال الفاشل يسجل
  فشلًا منقحًا، والتسليم المكرر لا يعيد تشغيل حالة غير `queued`.
- كل الإخراج والبيانات الوصفية محدودة ومنقحة؛ لا يعرض API بيانات الاعتماد.
- طلب الإلغاء قبل بدء العملية يحول المهمة إلى `cancelled`، وطلب الإلغاء
  أثناء التنفيذ يسجل كطلب ولا يدعي إيقاف عملية غير قابلة للمقاطعة.
- لا إعادة محاولة تلقائية لعملية ذات نتيجة غير مؤكدة بعد انقطاع العامل؛
  إعادة المحاولة اليدوية فقط بعد التحقق من الحالة وحد المحاولات.

### 6. API والواجهة

- `GET /api/v1/tasks/`: قائمة مرقمة مع مرشحات الحالة والعملية والخادم.
- `GET /api/v1/tasks/{uuid}/`: تفاصيل آمنة وسجل محدود ومتسلسل.
- `POST /api/v1/tasks/{uuid}/cancel/`: طلب إلغاء مصرح به.
- `POST /api/v1/tasks/{uuid}/retry/`: إعادة إرسال فشل/مهلة فقط مع تحقق
  dispatcher وحد المحاولات.
- تستخدم واجهة الويب خدمات المهمة نفسها، وتظهر صراحة حالة الطابور ورسالة
  غياب العامل؛ لا تعد المهمة ناجحة لمجرد إنشاء السجل.

### 7. الصلاحيات

- القراءة: `task.view` أو التوافق القديم `tasks_manage`.
- الإلغاء: `task.cancel` أو `tasks_manage`.
- إعادة المحاولة: `task.retry` أو `tasks_manage`، مع تحقق ثانٍ من صلاحية
  العملية الأصلية والهدف عبر Infrastructure Engine.
- تظل صلاحيات العملية الأصلية مطلوبة عند التنفيذ؛ صلاحية إدارة المهام لا
  تتجاوز تفويض العملية.

### 8. المهام الخلفية

- Celery يرسل UUID فقط؛ العامل يقرأ بيانات العملية من قاعدة البيانات.
- broker مضبوط وحده لا يثبت أن العامل حي؛ لا صحة شكلية أو تنفيذ fallback.
- حدود الوقت من إعدادات Celery، ومصالحة المهام المتقادمة توسم المهام
  `timeout` دون إعادة تنفيذ تخمينية.
- لا يتطلب الاختبار اتصال Redis؛ يغطي النشر بمحاكاة، وعلى المشغل التحقق من
  اتصال النشر والعامل في بيئته قبل تمكينه.

### 9. المحولات

- `InfrastructureEngine` يوجه إلى المحولات المسجلة ذات المدخلات المحددة.
- طبقة Celery/Redis ناقل اختياري؛ لا تتلقى أوامر تشغيل.
- لا محول عام للأوامر ولا استدعاء مباشر من Views إلى النظام.

### 10. الأحداث والتدقيق

- تدقيق إنشاء المهمة وانتقال حالتها ومحاولة الإلغاء وإعادة الإرسال.
- سجل كل مهمة منقح ومحدود، مع الفشل المصنف دون تفاصيل نقل أو أسرار.
- لا إشعار مستقل حتى ربط المرحلة بقناة Notifications لاحقًا.

### 11. الاعتماديات

تعتمد على Accounts للصلاحيات وحالة الحساب، Core للتدقيق والاستجابات، و
Infrastructure Engine/ManagedHost للتحقق والتنفيذ؛ وتقدم Dashboard واجهة
الويب. Celery وRedis اعتمادي تشغيل اختياريان للإرسال فقط، لا للاختبارات أو
حفظ البيانات.

### 12. اختبارات القبول

- إثبات رفض مدخلات العملية غير المسجلة، والصلاحيات/الحسابات/الأهداف غير
  الصحيحة، ومنع تشغيل العملية خارج المحرك.
- إثبات ترقيم API ومرشحاتها وخصوصية حقول المهمة والسجلات، وحالات 401/403/404
  والتحقق، وصيغ الاستجابات الموحدة.
- اختبار cancel قبل التنفيذ وأثناءه دون الإبلاغ كذبًا عن إيقاف أثر بدأ.
- اختبار retry للحالات المسموحة فقط وحد المحاولات، وإعادة تفويض العملية.
- اختبار dispatch مغلق، وفشل النشر، والتسليم المكرر، والمهلة، والسجل المنقح،
  وحدود الحجم، والتدقيق.
- تطبيق migrations وفحص Django، واختبار API والصلاحيات وتدفق Task Center ثم
  مجموعة المشروع كاملة.

### حدود القبول

لا تضمن هذه المرحلة اكتشاف صحة العامل من الويب، ولا إيقاف عملية نظام بعد
بدئها، ولا إعادة تنفيذ تلقائية آمنة لعملية ذات أثر غير معلوم. تظل العمليات
المسموحة محدودة إلى القائمة الحالية فقط.

**حالة القبول:** منفذة ومتحقق منها. لا ترحيلات جديدة مطلوبة؛ اجتازت فحوصات
Django وفحص الترحيلات و91 اختبارًا على مستوى المشروع، بما فيها REST API
للمهام، والصلاحيات المنفصلة، والإلغاء، وإعادة المحاولة، وتدفق Task Center.

## مواصفة تنفيذ المرحلة 4: إدارة Docker

تضيف هذه المرحلة سجلًا موحدًا لمحرك Docker المحلي وجرده، وتدعم إجراءات دورة
حياة حاويات محددة عبر Infrastructure Engine وTask Manager فقط. لا تعني
المرحلة أن Docker آمن افتراضيًا: تبقى الكتابة معطلة بإعداد مستقل، لأن وصول
Docker socket يمنح امتيازًا يقارب root على المضيف.

### 1. الغرض

- ربط كل محرك Docker بخادم `ManagedHost` واحد وعدم اختراع مضيف مستقل.
- جلب معلومات المحرك والحاويات والصور والشبكات والأحجام وCompose من SDK رسمي،
  مع حفظ زمن الرصد ومصدره وحالة التوفر.
- عرض الجرد الحي/المحفوظ بوضوح؛ لا تُظهر اللقطة المتقادمة على أنها الحالة
  الحالية.
- بدء/إيقاف/إعادة تشغيل/إيقاف مؤقت/استئناف/حذف حاوية عبر عمليات Typed ذات
  صلاحيات خاصة وإرسال خلفي فقط.
- عدم دعم إنشاء حاوية أو تنفيذ أمر داخلها أو حذف volume/image/network أو
  تعديل Compose في هذا النطاق؛ تحتاج هذه العمليات مواصفات ومراجعات منفصلة.

### 2. المكونات الداخلية

- نماذج `DockerEngine` و`DockerContainer` و`DockerImage` و`DockerVolume` و
  `DockerNetwork` و`ComposeProject` داخل `apps.containers`.
- `DockerAdapter` يعزل Docker SDK، يقيد endpoint إلى socket محلي معلوم،
  ويعيد بيانات منقحة ومحدودة.
- خدمة اكتشاف تحفظ اللقطة في معاملة واحدة، وتزيل الموارد غير الموجودة من
  الجرد الحالي بعد جمع كامل ناجح فقط.
- عمليات المحرك تطبق تفعيل الكتابة/الصلاحية/الحالة الحديثة/التأكيد ثم تحيل
  التنفيذ إلى `Task`.
- واجهات الويب الحالية تعرض inventory وسجلات الحاويات وتوفر إجراءات مصرحًا
  بها؛ API مرتبطة بـ`/api/v1/docker/`.

### 3. النماذج والحقول

- `DockerEngine`: علاقة One-to-One مع `ManagedHost`، endpoint محلي افتراضي،
  `enabled`, الحالة، إصدارات المحرك/API، معلومات آمنة JSON، آخر فحص ووقت
  الإنشاء/التعديل.
- `DockerContainer`: محرك، معرف Docker كامل وفريد ضمن المحرك، الاسم، image
  reference، الحالة/health، ports، networks، mounts، زمن الإنشاء/البدء،
  وقت الرصد؛ لا تحفظ البيئة أو الأسرار أو command line.
- `DockerImage`: المحرك، image ID، repository/tags، الحجم، وقت الإنشاء، وقت
  الرصد.
- `DockerVolume`: المحرك، الاسم الفريد، driver، mount point/labels المنقحة،
  containers المرتبطة ووقت الرصد؛ لا تعرض محتوى الملفات.
- `DockerNetwork`: المحرك، المعرف والاسم، driver/scope/subnet/gateway،
  containers المرتبطة ووقت الرصد.
- `ComposeProject`: المحرك، الاسم، الحالة، قائمة الخدمات الآمنة، وقت الرصد؛
  لا نخزن ملفات YAML أو environment values في هذه المرحلة.
- لا تتغير نماذج الخادم أو سجلات المهمة؛ جميع الموارد تابعة لمحرك مربوط
  بالمضيف المرجعي.

### 4. العلاقات

كل موارد Docker تابعة لمحرك، والمحرك مربوط بخادم واحد. هوية حاوية/صورة/
شبكة/volume مقيدة وفريدة داخل محركها. عند حذف الخادم، يمنع حذف المحرك مع
وجود metadata تشغيلية أو ينفذ cascade موثق وفق السياسة المختارة في النموذج.
المهمة تشير إلى ManagedHost وتخزن operation وresource ID المنقح؛ لا تنسخ
بيانات الحاوية إلى المهمة.

### 5. الخدمات والمنطق

- endpoint مسموح فقط Unix socket؛ لا TCP endpoint ولا عنوان HTTP من قاعدة
  بيانات يسبب اتصالًا شبكيًا غير مقصود.
- discovery يحد عدد العناصر والحقول وحجم metadata ويضع `observed_at`؛ لا
  يعتبر timeout أو فشل SDK جردًا فارغًا ناجحًا.
- العملية تستخدم ID كاملًا موجودًا في الجرد الحديث لنفس المحرك، وترفض حاوية
  غير معروفة/قديمة/من محرك آخر، وتعيد التحقق في العامل قبل الأثر.
- remove لا يستخدم force، ولا يحذف volumes؛ stop/restart/pause تتطلب تأكيدًا
  صريحًا. operation لكل نوع فعل وصلاحية مستقلة.
- لكل مهمة أثر مدقق ونتيجة منقحة، ولا يوجد نداء SDK تغييري في View.
- تثبيت SDK غير متاح أو Docker daemon غير مهيأ يظهر `unavailable`؛ لا تظهر
  بيانات تشغيل موهومة.

### 6. API والواجهة

- `GET /api/v1/docker/engines/` و`GET /api/v1/docker/engines/{id}/` لعرض
  المحركات والجرد.
- `POST /api/v1/docker/engines/` يسجل محركًا لمضيف محلي مفعّل؛ body هو
  `{"server_id": 1}` فقط، ويتطلب `docker.engine.manage`.
- `POST /api/v1/docker/engines/{id}/discover/` يرسل الاكتشاف المحدود.
- `POST /api/v1/docker/engines/{id}/containers/{container_id}/{action}/`
  يرسل فعلًا مسجلًا فقط ويعيد `202` مع Task UUID؛ body هو
  `{"confirmation": true}` فقط ولا يقبل command أو endpoint.
- لوحة الحاويات والموارد والسجلات تقرأ الجرد المحفوظ لا اتصالًا حيًا متزامنًا؛
  تعرض تقادم الجرد. قراءة السجلات تستخدم SDK المحلي، 1–200 سجل، وتخفي القيم
  الحساسة.
- العرض والتصفية حسب المحرك/الحالة؛ سجلات الحاويات تبقى محدودة ومنقحة.
- إجراءات التغيير لا تظهر عندما يكون Docker writes أو Task Dispatcher
  معطلًا، ويظهر سبب التعطيل للمشغل.

### 7. الصلاحيات

- القراءة: `docker.container.view` (وتضاف صلاحيات منفصلة للمحركات والصور/
  الشبكات/الأحجام إذا فتحت APIs لهذه الموارد).
- الأفعال: `docker.container.start`, `.stop`, `.restart`, `.delete`؛
  تضاف صلاحيات pause/resume إلى الكتالوج. كل طلب يتطلب `task.view` أو
  `tasks_manage` بالإضافة لصلاحية الفعل، ويتحقق العامل من صلاحية الفعل مجددًا.
- الكتابة معطلة افتراضيًا بإعداد `INFRA_DOCKER_WRITE_ENABLED=False`، ولا
  تكفي الصلاحية لتجاوز تعطيلها.

### 8. المهام الخلفية

جميع التغييرات عبر Task Manager. UUID وحده يمر في Celery؛ worker يعيد تحميل
المورد والتحقق من حالته ويفوض إلى محول Docker بعد إعادة التفويض. فشل نشر
المهمة لا ينفذ الفعل بشكل مباشر.

### 9. المحولات

- Docker SDK محلي، مع مهلات صريحة للاتصال والقراءة والكتابة ومخرجات JSON
  محدودة.
- لا تنفذ عمليات باستخدام CLI strings؛ لا SDK إلى remote TCP endpoint.
- ليس في هذه المرحلة Docker exec أو file copy أو bind mounts أو privileged
  container creation.

### 10. الأحداث والتدقيق

- كل discovery يسجل تحديث/تعذر بيانات المحرك.
- كل فعل ينشئ Task وAuditLog؛ يسجل حالة المورد بعد إعادة الفحص إذا أمكن.
- لا توهم الواجهة بأن التغيير اكتمل بمجرد قبول task.

### 11. الاعتماديات

تعتمد `apps.containers` على Infrastructure للخادم وEngine للتحقق، Tasks
للتنفيذ، Security/Accounts للصلاحيات، Core للتدقيق، Dashboard للعرض.
تعتمد عملية Docker الفعلية على Docker SDK وdaemon/socket المحلي فقط.

### 12. اختبارات القبول

- migrations والعلاقات والقيود الفريدة وعزل الموارد بين engines.
- discovery ناجح وفارغ وفاشل وtimeout وSDK غائب ونتائج كبيرة، دون حذف snapshot
  سابق عند الفشل.
- منع endpoints غير المحلية، وإثبات عدم كشف env/secrets/commands أو الملفات.
- أفعال Typed تتحقق من صلاحية منفصلة، الإعداد الافتراضي المغلق، التأكيد،
  الجرد الحديث، حدود الموارد وحالة المحرك.
- إثبات أن Views لا تنادي SDK تغييريًا وأن العمليات تستخدم Task/Engine،
  مع فشل dispatch والتكرار والتدقيق.
- API وواجهة وصلاحيات وروابط السجل، وعدم تعطل بقية الوحدات.
- Django checks والترحيلات وجميع الاختبارات قبل إعلان قبول المرحلة.

**حالة القبول:** اجتازت المرحلة 120 اختبارًا على مستوى المشروع، بما فيها
اكتشاف وجرد Docker المحاكى، الحالات الفاشلة والمهل وحدود النتائج، العلاقات،
الصلاحيات، API والواجهة. نجحت فحوص Django و`makemigrations --check`، وطُبق
`containers.0001` على قاعدة التشغيل. أعادت صفحة `/dashboard/inventory/` ولوحة
Docker وواجهة المحركات HTTP 200 بعد الترحيل. لم يُجر اكتشاف حي من daemon؛
`INFRA_DOCKER_READ_ENABLED` معطل افتراضيًا ولا يوجد محرك مسجل.

## مواصفة تنفيذ المرحلة 5: أتمتة Ansible المعتمدة

### 1. الغرض

توسيع تكامل Semaphore الحالي إلى مسار أتمتة مضبوط وقابل للتدقيق: كتالوج
للقوالب المعتمدة، ونطاق خادم واحد معروف من سجل `ManagedHost`، ومدخلات معلنة
ومتحقق منها، وجدولة دورية آمنة للاختبار الجاف، وتنفيذ يمر عبر Infrastructure
Engine وTask Manager. يظل Semaphore محول التنفيذ خلال الانتقال؛ لا ينفذ تطبيق
Django ملفات playbook أو أوامر Ansible محليًا.

### 2. المكونات الداخلية

- كتالوج `ApprovedTaskTemplate` الحالي مع مخطط مدخلات محدود ومراجعة/اعتماد صريح.
- `ManagedHost.ansible_limit` هو حد المضيف الوحيد؛ لا تنشئ المرحلة نسخة أخرى
  من جرد الخوادم ولا تسمح بنطاق `all` أو wildcards أو مجموعات عامة.
- خدمة تحقق للمدخلات، وخدمة طلب تشغيل تنشئ `AutomationRun` ثم Task typed.
- عملية `automation.template.execute` مسجلة في Infrastructure Engine، تعيد
  التحقق في العامل قبل استدعاء Semaphore.
- `AutomationSchedule` يشغّل الاختبار الجاف فقط من أمر إدارة مجدول بنظام التشغيل.
- واجهة كتالوج وتشغيل وتاريخ، وصفحة تفاصيل مع تحديث حالة ومخرجات منقحة.

### 3. النماذج والحقول

- `ApprovedTaskTemplate` (قائم): المشروع والقالب والفئة والوصف والحالة
  `enabled` و`read_only` و`requires_confirmation` وارتباط اختياري بالخادم
  والخدمة؛ يضاف `variables_schema` لتعريف أسماء وأنواع وقيم اختيارية مسموحة.
- `AutomationRun` (قائم): القالب والفاعل ومعرف مهمة Semaphore والحالة والنمط
  والملخص والمخرجات؛ يضاف Task محلي اختياري، حد المضيف الفعلي، ونسخة منقحة من
  القيم غير السرية الممررة.
- `AutomationSchedule` (جديد): قالب معتمد، منشئ، تفعيل، فترة بالدقائق (15
  دقيقة على الأقل)، `next_run_at`، آخر إطلاق، حالة/خطأ آخر إطلاق، وقيم
  متغيرات مشفرة وأسماء الحقول فقط. الجدولة المسموحة في هذه المرحلة dry-run فقط.

### 4. العلاقات

- القالب يرتبط بـ`ManagedHost` و/أو `ManagedService` كما في النموذج الحالي؛
  التشغيل يتطلب خادمًا فعالًا وحدًا صريحًا صالحًا، ويحتفظ بتاريخ المرجع حتى
  تعطيل القالب.
- التشغيل يرتبط اختياريًا بـ`apps.tasks.Task`؛ مصدر المهمة هو سجل
  `AutomationRun`، والمرجع محفوظ من الجهتين.
- الجدول يرتبط بقالب واحد؛ تشغيلاته تظهر في `AutomationRun` ولا تنشئ جداول
  أو خوادم مكررة.
- حذف القالب ذي تشغيلات أو جداول تاريخية محمي بـ`PROTECT`.

### 5. الخدمات ومنطق الأعمال

- لا يستورد الكتالوج عن بعد قالبًا مفعّلًا؛ تتطلب الموافقة مديرًا ونطاق خادم
  صالحًا. قوالب الاستعادة تظل خاضعة لإذنها وتأكيد `RESTORE` المنفصل.
- مخطط المتغيرات يقبل أسماء آمنة وقيمًا scalar ذات نوع محدد فقط، مع حدود
  الحجم والاختيارات؛ يمنع مفاتيح/قيم الأسرار من التخزين في سجلات المهام.
- التشغيل الجاف هو الافتراضي. التشغيل الحي يتطلب صلاحية التنفيذ، سياسة القالب
  غير المقروء فقط، تأكيدًا صريحًا، وموافقة الاستعادة الإضافية عند انطباقها.
- العامل يعيد فحص هوية الفاعل وصلاحيته وحالة اعتماد القالب ونطاق المضيف
  والمدخلات، ثم يبدأ مهمة Semaphore؛ لا تعتبر المهمة المحلية اكتمال playbook:
  `AutomationRun` يتتبع الحالة الخارجية ويعرض إخفاق الاتصال صراحة.
- المجدول يطلق تشغيلًا جافًا فقط، يحدّث موعده ذريًا ويمنع الإطلاق المكرر.
  التشغيل الحي المجدول خارج النطاق.

### 6. APIs والواجهات

- تُحافظ على مسارات لوحة التحكم الحالية: `/dashboard/automation/templates/`,
  الإنشاء/الاعتماد، `/dashboard/automation/templates/<id>/run/`، تفاصيل التشغيل
  والتحديث.
- نموذج التشغيل يقبل قيم المتغيرات المعلنة فقط؛ لا نقطة REST جديدة في هذه
  المرحلة. جميع أفعال الإنشاء والتشغيل والتحديث POST محمية CSRF.
- أمر `dispatch_due_automation_schedules` هو واجهة الجدولة، ويعمل من cron أو
  systemd timer كل دقيقة مع عامل المهام المهيأ.

### 7. الصلاحيات

- العرض: `automation.playbook.view` أو صلاحية عرض البنية التحتية المتوافقة.
- الاعتماد والإدارة: `automation.playbook.create` أو رمز التوافق
  `infrastructure_manage`.
- التشغيل: `automation.playbook.execute` و`task.view`؛ يقبل رمز الإدارة القديم
  للتوافق خلال الانتقال.
- إدارة الجداول تتطلب صلاحية الإدارة، ويعيد العامل فحص الفاعل عند التنفيذ.
- تبقى صلاحيات `backup_restore` وتأكيد `RESTORE` مطلوبة لاستعادة النسخ.

### 8. المهام الخلفية

- كل تشغيل يدوي يمر عبر Task Manager عند تفعيل Celery/Redis؛ فشل الإرسال ظاهر
  كسجل تشغيل فاشل ولا يوجد تنفيذ متزامن بديل في طلب الويب.
- أمر الجدولة لا ينفذ العمل؛ ينشئ مهمة عبر نفس خدمة التشغيل ويدفعها إلى العامل.
- لا polling طويل داخل عامل Celery؛ حالة playbook الخارجية تُحدّث عند طلب
  التفاصيل/التحديث. إخفاق الاتصال لا يُفسر على أنه نجاح أو فشل للمهمة الخارجية.

### 9. محولات البنية التحتية

- Semaphore API فقط: HTTPS للمضيفات البعيدة، localhost فقط دون HTTPS، مهلة
  وقراءة استجابة محدودتان، bearer token من إعداد سري، ونقاط API ثابتة.
- لا Ansible CLI أو shell أو inventory نصي أو ملف playbook يقدمه المستخدم.
- يعاد استخدام Adapter العميل الحالي ويصحح ترويسة Bearer إن لزم؛ لا يتصل أي
  اختبار بـSemaphore حقيقي.

### 10. الأحداث والتنبيهات

- سجل التدقيق يغطي الإنشاء والتعديل والاعتماد والتشغيل والجدولة والإخفاق.
- TaskLog والمخرجات الخارجية محدودة ومنقحة؛ لا تسجل رموز الوصول أو قيم
  المتغيرات المحظورة.
- لا تضيف المرحلة قناة إشعارات مستقلة؛ ذلك ضمن مرحلة Notifications.

### 11. الاعتماديات

تعتمد على Accounts/Permissions وCore/Audit وInfrastructure (`ManagedHost`) و
Infrastructure Engine وTasks. تعتمد خارج التطبيق على Semaphore اختياريًا؛
غيابه يظهر بوضوح ولا يعطل بقية اللوحة.

### 12. سيناريوهات القبول

- migrations تحفظ القوالب والتشغيلات الموجودة؛ نموذج الجدول وحدود القيم والروابط.
- اعتماد قالب بلا خادم/حد صالح أو بنطاق `all`/wildcard مرفوض.
- تحقق مخطط المتغيرات للأنواع والاختيارات والحقول الإضافية والحجم والأسرار.
- تشغيل dry-run/live مع صلاحيات صحيحة وخاطئة، تأكيد، وقوالب read-only/restore.
- إثبات أن الطلب لا يتصل بـSemaphore ولا ينفذ مباشرة، وأن المهمة تعيد التحقق
  في العامل وتستخدم حدًا دقيقًا واحدًا.
- Semaphore غير مهيأ/timeout/HTTP غير ناجح/استجابة غير صحيحة؛ لا نجاح زائف،
  ولا تسريب رمز أو قيم متغيرات.
- جدولة dry-run بلا تكرار، وعدم إطلاق live schedules، واحترام تعطيل القالب.
- واجهة القائمة والتفاصيل والتحديث والصلاحيات وسجل التدقيق وروابط Tasks.
- Django checks، عدم وجود migrations ناقصة، والاختبارات ذات الصلة قبل قبول
  المرحلة أو بدء المرحلة 6.

**حالة القبول:** اجتازت المرحلة **132 اختبارًا** على مستوى المشروع. نجحت
`manage.py check` و`makemigrations --check --dry-run`؛ وطُبقت
`automation.0003` و`automation.0004` على قاعدة SQLite بعد حفظ نسخة
`/tmp/infrastructure-manager-before-automation.sqlite3`. اختبارات Semaphore
والطابور تستخدم محاكاة؛ لم يُشغّل playbook حي ولا عامل/وسيط حقيقي. اكتملت هذه
المرحلة ضمن محول Semaphore المعتمد؛ تأليف playbooks وجرد متعدد المضيفين داخل
التطبيق ما زالا خارج النطاق.

## مواصفة تنفيذ المرحلة 6: المراقبة والتنبيهات

### 1. الغرض

توحيد جمع قياسات CPU والذاكرة والجذر والشبكة للخوادم المفعلة عبر المصادر
المهيأة، وإظهار نجاح أو فشل كل محاولة، وتقييم قواعد العتبات بدورة حياة قابلة
للتدقيق، مع احتفاظ مضبوط وواجهات لوحة وREST صريحة. سجل `ManagedHost` هو مصدر
الأهداف؛ لا تنشئ المرحلة جرد خوادم مكررًا.

### 2. المكونات الداخلية

- هدف قياس مشتق من `ManagedHost.is_local` أو `prometheus_instance`؛ حالة
  الموفر غير المهيأ تبقى ظاهرة ولا تتحول إلى صفر.
- `MetricsService` لمهايئات Linux procfs وPrometheus/Node Exporter.
- `MetricCollection` جديد لتسجيل كل محاولة ناجحة/فاشلة وربط القياس المحفوظ.
- `ResourceSample` للقياسات الناجحة، و`AlertRule` لتعريف العتبات، و`AlertEvent`
  لحالة التنبيه والتنبيه بالبريد.
- أمر `collect_infra_metrics` مجدول من النظام، وصفحة Alert lifecycle،
  وREST APIs للأهداف والعينات والقواعد والتنبيهات.

### 3. النماذج والحقول

- `ManagedHost` الحالي: هو الهدف المرجعي، ومصدره `is_local` و`prometheus_instance`.
- `ResourceSample` الحالي: المضيف، المصدر، CPU/ذاكرة/مساحة القرص/سرعة الشبكة،
  ووقت الالتقاط؛ القياسات غير المتاحة تبقى `NULL`.
- `MetricCollection` (جديد): المضيف، المصدر، النتيجة `success|failed`،
  سبب الفشل الآمن، وقت المحاولة، وعلاقة اختيارية بعينة القياس.
- `AlertRule` الحالي: الاسم والقياس والعتبة ومدة التهدئة والتفعيل؛ تفرض حدود
  المجال على النسبة المئوية ومدة التهدئة.
- `AlertEvent` الحالي: القاعدة والمضيف والعنوان والرسالة والإقرار؛ يضاف
  `resolved_at`, `last_seen_at`, `occurrences`, وحالة/خطأ/توقيت إرسال البريد
  كي تكون الإخفاقات والتكرارات ظاهرة.

### 4. العلاقات

- محاولات القياس وعيناته تتبع `ManagedHost`، ولا تحذف الخادم أو سجلات المحاولة
  ضمنيًا؛ حذف العينة القديمة لا يحذف سجل محاولة الجمع.
- العينة مرتبطة بمحاولة ناجحة واحدة. محاولة فاشلة لا تنشئ عينة نجاح مصطنعة.
- الحدث يشير إلى قاعدة ومضيف؛ التقييم يقفل سجل المضيف ويحدث الحدث المفتوح
  داخل معاملة واحدة لمنع التكرارات، بينما يحتفظ بالأحداث المحلولة كتاريخ.
- تظل العينات ومحاولات التجميع محدودة بالاحتفاظ؛ لا تُحذف أحداث التنبيه
  التاريخية تلقائيًا في هذه المرحلة.

### 5. الخدمات ومنطق الأعمال

- لا تجمع الخدمة هدفًا أسرع من `monitoring_collection_interval_seconds`؛
  تتجاوز الهدف المبكر بوضوح. كل فشل موفر يحفظ كـ`MetricCollection.failed`.
- تحفظ العينة فقط عند إتاحة القياسات؛ القيم المفقودة `NULL`، ولا يقيم العداد
  قاعدة على قيمة غير متاحة.
- العتبة المتجاوزة تفتح أو تحدّث الحدث النشط؛ التكرار يزيد `occurrences` ووقت
  آخر مشاهدة دون إنشاء تنبيه مكرر. الإشعار يعاد فقط بعد `cooldown_minutes`.
- عودة القياس تحت العتبة تحل الحدث؛ تعطيل القاعدة يحل الأحداث النشطة عند
  التقييم التالي. الإقرار لا يحل الحدث تلقائيًا.
- يمسح الأمر العينات ومحاولات الجمع الأقدم من `metrics_retention_days` في كل
  تشغيل، حتى عند فشل كل الموفرات.
- فشل البريد لا يسقط نتيجة القياس ولا يختفي؛ تحفظ فئة خطأ آمنة وحالة الإرسال.

### 6. APIs والواجهات

- REST `/api/v1/monitoring/targets/`, `/samples/`, `/rules/`,
  `/rules/{id}/`, `/collections/`, `/alerts/`, و
  `/alerts/{id}/acknowledge/`.
- قوائم الأهداف/العينات/محاولات الجمع/الأحداث مرقمة؛ تقبل معاملات `host`,
  و`since` للعينات، و`status` لمحاولات الجمع، و`state` للتنبيهات (`open`,
  `acknowledged`, `resolved`, `all`) وتعيد غلاف API الموحد.
- صفحة `/dashboard/alerts/` تعرض آخر 100 حدث وآخر 50 محاولة جمع، وحالات
  الأحداث المفتوحة والمعترف بها والمحلولة،
  مرات التكرار وآخر مشاهدة وحالة البريد؛ الإنشاء/الإقرار POST مع CSRF.

### 7. الصلاحيات

- القراءة: `monitoring.view` أو صلاحية عرض البنية التحتية المتوافقة.
- إنشاء/تعديل القواعد: `monitoring.alert.manage` أو `infrastructure_manage`.
- إقرار التنبيه: `monitoring.alert.acknowledge` أو `infrastructure_manage`.
- هوية العامل المجدول لا تمنح صلاحيات مستخدم؛ الجمع للقراءة، وكل تعديل قاعدة
  أو إقرار يسجل فاعله في التدقيق.

### 8. المهام الخلفية

- `collect_infra_metrics` مجدول من cron أو systemd timer حسب فترة الإعداد
  المخزنة. لا تنفذ صفحات الويب جمعًا بطيئًا ولا ترسل المهمة للمستخدم.
- شغّل `python manage.py collect_infra_metrics` من cron/systemd timer؛
  الفاصل المخزن يحد الجمع لكل مضيف، لذا يوصى بتكرار الأمر كل 15 ثانية على
  الأقل إذا احتاج النشر دقة الفاصل الأدنى.
- ينفذ الجمع الاحتفاظ وتقييم القواعد لكل هدف، ويخرج فشلًا غير صفري عند وجود
  موفرات فاشلة بعد حفظ نتائجها.
- لا يحتاج الجمع إلى Celery؛ إعادة تشغيل الأمر آمنة بالنسبة لتكرار التنبيه،
  والحد الأدنى للفاصل يمنع الإفراط في القياس.

### 9. محولات البنية التحتية

- Local procfs للهدف المحلي فقط، وPrometheus API عند تهيئة عنوان موثوق وتسمية
  Node Exporter صحيحة.
- استعلامات Prometheus ثابتة، مع timeout وحجم استجابة محدودين؛ HTTPS إلزامي
  للوجهة البعيدة، وHTTP مسموح محليًا فقط. لا يقبل المستخدم تعبير PromQL.
- لا يتصل أي اختبار بمضيف أو Prometheus حقيقي؛ حالات adapter تحاكى.

### 10. الأحداث والتنبيهات

- ينشأ/يحدّث/يحل `AlertEvent` ضمن دورة تقييم ثابتة؛ الإقرار وتعديل القواعد
  يسجلان في AuditLog.
- ينشئ الحدث إشعارًا شخصيًا عبر Notifications وفق صلاحية المستخدم وتفضيلاته؛
  لا يرسل جامع القياسات SMTP ضمن عملية الجمع.
- سجل البريد ومحاولات إعادة التسليم يملكهما Notifications، وتظهر حالة
  التسليم في سجل الإشعار والتنبيه المصدر.

### 11. الاعتماديات

تعتمد على Core لإعدادات الفاصل والاحتفاظ والتدقيق، وInfrastructure لهوية
الخوادم، وAccounts للصلاحيات، وDashboard للعرض، وNotifications لتوجيه الأحداث.
Prometheus اختياري ويظهر عدم تهيئته كحالة صريحة.

### 12. سيناريوهات القبول

- migrations تحفظ العينات والتنبيهات الحالية وتضيف سجل المحاولات والقيود.
- نجاح/فشل/انقطاع/استجابة جزئية لمهايئي Linux وPrometheus، مع عدم تحويل
  القياس المفقود إلى صفر وتسجيل الفشل.
- احترام فترة الجمع والاحتفاظ لكل من العينات والمحاولات حتى عند غياب القياس.
- تجاوز العتبة يفتح حدثًا واحدًا تحت التكرار المتزامن، ويحدث `occurrences`
  ويراعي cooldown؛ عودة الصحة تحل الحدث، وتعطيل القاعدة يحل النشط.
- حدث تنبيه يرسل إشعارًا موجهًا إلى مستخدمي monitoring المخولين؛ البريد
  الافتراضي معطل، وتختبر إعادة المحاولة ضمن قبول Notifications.
- API pagination والمرشحات والصلاحيات والغلاف، وإقرار مكرر idempotent.
- اختبار لوحة alerts وقواعد القياس وصلاحياتها، Django checks وmigrations
  وجميع الاختبارات قبل اعتماد مرحلة Monitoring.

**نتيجة التنفيذ والقبول:** أضيف `MetricCollection` وسجل دورة حياة التنبيه،
وأصبحت الواجهات ذات صلاحيات منفصلة، كما تسجل حالات فشل مزود القياس. تُسجل
حالات البريد وتكرار المحاولة الآن عبر وحدة Notifications.
اجتازت المرحلة **18 اختبارًا مخصصًا**، واجتاز المشروع **150 اختبارًا**؛ ونجحت
فحوص Django وغياب ترحيلات معلقة. طُبق الترحيل
`monitoring.0003_metriccollection_and_more` على قاعدة SQLite بعد أخذ نسخة
احتياطية.

## مواصفة تنفيذ المرحلة 7: النسخ الاحتياطي والاستعادة

### 1. الغرض

إدارة دورة النسخ والاستعادة من لوحة تحكم موثوقة دون تنفيذ ملفات أو أوامر نسخ
احتياطي داخل Django. يمر العمل فقط عبر قوالب Semaphore/Ansible معتمدة؛ لا
يُسجل artifact ناجح إلا عند اكتمال المهمة الخارجية وتقديم إيصال بيانات وصفية
صحيح. تُربط الاستعادة بartifact ناجح محدد، لا بمسار يختاره طالب الطلب.

### 2. المكونات الداخلية

- `BackupPolicy` يربط خدمة وقالب Backup معتمدًا، وسياسة الاحتفاظ، وفاصل
  التشغيل المجدول وحالة الجدولة.
- `BackupArtifact` سجل metadata مرتبط بتشغيل `AutomationRun`، بحالات pending,
  success, failed, unknown وإيصال محدود/منقح.
- `BackupRestoreRequest` سجل يربط artifact مصدرًا بتشغيل Restore وفاعله.
- خدمة لإنشاء تشغيل Backup حي معتمد، والتحقق من إيصال Semaphore وتحديث artifact
  بتكرار آمن، وخدمة لطلب Restore من artifact محدد.
- أمر `dispatch_due_backup_policies` لإرسال النسخ المجدولة عبر Task Manager.
- صفحات ولوحة وواجهات REST لإدارة السياسات، التشغيل اليدوي، مراجعة artifacts،
  وتحديثها وطلب الاستعادة.

### 3. النماذج والحقول

- `BackupPolicy`: اسم فريد، خدمة مطلوبة، قالب Backup مطلوب، `retention_count`
  موجب، `interval_minutes` مضبوط (15–10080)، `enabled` معطل افتراضيًا،
  `created_by`, `next_run_at`, `last_run_at`, `last_error`. يحتفظ حقل
  `schedule` القديم للتوافق ولا يُستخدم للتنفيذ.
- `BackupArtifact`: المضيف والخدمة والسياسة، `automation_run` فريد اختياري
  للتوافق مع السجلات السابقة، اسم الملف، مرجع تخزين نسبي، الحجم، SHA-256،
  الحالة، وخطأ التحقق. لا تُخزن محتويات النسخة أو أسرارها في قاعدة Django.
- `BackupRestoreRequest`: artifact المصدر، تشغيل Automation المرتبط، الفاعل
  وتاريخ الطلب؛ حالة التنفيذ المحدثة مصدرها `AutomationRun`.
- لا يحتاج `AutomationRun` إلى تخزين نسخة ثانية من بيانات الملف؛ سجل artifact
  يشير إليه بمفتاح فريد.

### 4. العلاقات

- السياسة ترتبط بخدمة واحدة وقالب `BACKUP` معتمد، ويجب أن يطابق القالب الخدمة
  والخادم. المضيف وحد Ansible مصدرهما `ManagedService` و`ManagedHost`.
- كل تشغيل سياسة ينشئ `AutomationRun` ومقابله `BackupArtifact` واحدًا؛ تحفظ
  السجلات التاريخية عند تعطيل السياسة أو القالب.
- الاستعادة لا تقبل إلا artifact ناجحًا له مرجع تخزين صالح، وقالب `RESTORE`
  معتمد ومحدود إلى مضيف/خدمة النسخة نفسها.
- حذف artifact أو تشغيله التاريخي لا يحدث ضمنيًا مع حذف السياسة؛ تُحفظ
  العلاقات التاريخية أو تمنع عملية الحذف ذات الصلة.

### 5. الخدمات ومنطق الأعمال

- يتطلب إعداد/تفعيل السياسة صلاحية النسخ، وقالبًا مفعّلًا من فئة BACKUP، وخدمة
  متوافقة، ومخطط القالب متغيرًا مطلوبًا `retention_count` من نوع integer.
- تفعيل السياسة هو موافقة صريحة على التشغيل الحي المجدول. لا تعمل السياسات
  الجديدة تلقائيًا. التشغيل اليدوي يتطلب تأكيدًا حيًا؛ الجدولة لا تقبل قوالب
  RESTORE ولا قوالب غير معتمدة.
- عند الإرسال يُمرر عدد الاحتفاظ كمتغير معلن، ويُنشأ artifact بحالة pending.
  الفشل المحلي أو الخارجي يسجله failed؛ نجاح Semaphore بلا إيصال صحيح يبقى
  unknown ولا يدعي النظام تحقق نسخة فعلية.
- صيغة الإيصال الوحيدة في خرج المهمة سطر مستقل
  `INFRA_BACKUP_ARTIFACT=<JSON>` مع `file_name`, `artifact_ref`,
  `size_bytes`, `sha256`. يُتحقق من الاسم والمرجع النسبي والحجم وبصمة SHA-256؛
  تُرفض الإيصالات المكررة أو غير الصالحة. الحالة success تعني نجاح المهمة
  وإيصال metadata صالحًا، ولا تعني أن Django قرأ الملف أو اختبر استعادته.
- Restore يحقن `backup_artifact_ref` من artifact المختار في قالب الاستعادة؛
  لا يسمح للعميل بإرسال هذا المرجع أو استبداله. يتطلب dry-run أولًا، وصلاحية
  ناجحًا لنفس artifact والقالب والمتغيرات، وصلاحية `backup.restore`، وموافقة
  `confirm=yes` وكتابة `RESTORE` قبل live. تُفك متغيرات dry-run المشفرة للتحقق
  من التطابق دون تسجيلها أو عرضها.
- الجدولة تقفل السياسة وتقدم الموعد ذريًا قبل الإرسال؛ لا تعاد جدولة تشغيل
  فائت تلقائيًا، وتُحفظ أخطاء الإرسال للعرض.

### 6. APIs والواجهات

- REST: `GET/POST /api/v1/backups/policies/`,
  `GET/PATCH /api/v1/backups/policies/{id}/`,
  `POST /api/v1/backups/policies/{id}/run/`,
  `GET /api/v1/backups/artifacts/`,
  `POST /api/v1/backups/artifacts/{id}/refresh/` و
  `POST /api/v1/backups/artifacts/{id}/restore/`.
- قوائم السياسات وartifacts مرقمة. التشغيل يعيد `AutomationRun`/`Task` ومراجعها
  لا نجاح النسخ؛ تحديث artifact يعيد الحالة الحالية أو unknown صراحة.
- لوحة `/dashboard/backups/` تعرض حالة الجدولة والـartifacts، وتوفر التشغيل
  اليدوي والتحديث والاستعادة المنضبطة. لا تعرض حقولًا أو مخرجات تحتوي أسرارًا.
- جميع الأفعال تغيّر الحالة عبر POST محمي CSRF؛ API يستخدم غلاف النواة.

### 7. الصلاحيات

- القراءة: `backup.view` أو صلاحية عرض البنية التحتية للتوافق.
- إنشاء/تعديل/تشغيل سياسة Backup: `backup.create` إضافة إلى صلاحيات التنفيذ
  و`task.view` المفروضة من Automation وTask Manager.
- الاستعادة: `backup.restore` (مع قبول الرمز القديم `backup_restore` في فترة
  التوافق)، وصلاحية Automation/Task، وتأكيد الاستعادة المكتوب.
- المجدول يعيد التحقق من نشاط منشئ السياسة وصلاحيته عند كل إرسال؛ لا ينفذ
  بهوية النظام أو صلاحية أوسع ضمنيًا.

### 8. المهام الخلفية

- كل Backup/Restore يمر عبر Infrastructure Engine وTask Manager إلى عامل
  Celery ثم Semaphore. لا fallback تنفيذيًا داخل طلب الويب.
- `dispatch_due_backup_policies` يعمل من systemd timer أو cron كل دقيقة؛
  يعالج السياسات المستحقة فقط ويرصد الفشل دون إعادة تشغيل تلقائي.
- تحديث حالة Semaphore وخرج المهمة صريح عبر إجراء تحديث محمي؛ لا يعتمد سجل
  artifact على مجرد قبول Semaphore للطلب.
- عدم تكوين Redis/Celery يعيد حالة فشل ظاهرة ولا ينفذ العمل داخل Django.

### 9. محولات البنية التحتية

- إعادة استخدام `SemaphoreClient` بالقوالب المعتمدة فقط و`ManagedHost.ansible_limit`
  الدقيق. لا يُقبل shell أو playbook أو ملف أو مسار حر من المستخدم.
- لا يتصل Django بمخزن الملفات، ولا يرفع/يحذف/يستعيد محتوى نسخة. Semaphore
  هو المسؤول عن التنفيذ والتخزين والاحتفاظ الفعلي، مع إيصال metadata موحد.
- الاختبارات تحاكي Semaphore ولا تلمس ملفات أو خوادم أو قواعد بيانات حقيقية.

### 10. الأحداث والتدقيق

- إنشاء وتعديل وتفعيل سياسة، تشغيل يدوي/مجدول، تحديث حالة artifact، وطلب
  Restore تُسجل في `AuditLog` مع الفاعل والمرجع، دون قيم متغيرات أو محتوى
  النسخة.
- تُنقح مخرجات Semaphore قبل حفظها أو عرضها. إيصال غائب أو غير صالح وخطأ
  الوصول الخارجي حالات ظاهرة ومختلفة عن success.
- لا تُرسل إشعارات مستقلة خارج وحدة Notifications.

### 11. الاعتماديات

تعتمد على Infrastructure للخوادم والخدمات، وAccounts للصلاحيات، وAutomation
للقوالب المعتمدة وSemaphore، وTasks للإرسال والتنفيذ، وCore للتدقيق. تبقى
إدارة ملفات النسخ ومخزنها الخارجي مسؤولية القالب/البنية التحتية المهيأة.

### 12. سيناريوهات القبول

- ترحيلات تحافظ على سياسات وartifacts القديمة دون ربط مصطنع بتشغيل أو قالب.
- منع السياسة عند عدم تطابق القالب/الخدمة/المضيف أو غياب متغير الاحتفاظ
  المعلن، مع فشل ظاهر عند تعطل الإرسال.
- جدولة opt-in فقط، حد الفاصل، تكرار آمن، وفشل مجدول لا ينفذ inline.
- قبول إيصال واحد صحيح وربط idempotent؛ رفض بصمة أو حجم أو مسار غير صالح،
  إيصالات متعددة، أو نجاح Semaphore من دون receipt.
- Restore لا يقبل artifact pending/failed أو مضيفًا مختلفًا، ولا يسمح بتزوير
  المرجع، ويتطلب dry-run ناجحًا مطابقًا والصلاحية والتأكيدين للـlive.
- اختبار API pagination والصلاحيات والتدقيق، صفحات الويب لكل الحالات،
  ودورة التشغيل عبر mocks؛ ثم `check`, `makemigrations --check`, ومجموعة
  الاختبارات الكاملة قبل قبول المرحلة.

### نتيجة القبول

- اجتازت المرحلة اختبارات API والصلاحيات واللوحة وسير العمل عبر mocks؛
  أظهرت مجموعة المشروع الكاملة `171` اختبارًا ناجحًا.
- `manage.py check` و`makemigrations --check --dry-run` ناجحان، والترحيل
  `backup.0002` مطبق على قاعدة التشغيل. كانت أعداد السياسات وartifacts صفرًا
  قبل الترحيل وبعده؛ لم توجد سجلات قديمة لتحويلها.
- لم يُجر اتصال حي بـSemaphore أو Redis أو مخزن الملفات؛ يجب التحقق منها
  في بيئة النشر قبل تفعيل الجدولة الحية.

## مواصفة تنفيذ المرحلة 8: الإشعارات

### 1. الغرض

تقديم إشعارات فعلية موجهة للمستخدمين داخل التطبيق وبالبريد الاختياري، مع سجل
تسليم قابل لإعادة المحاولة وتفضيلات لكل مستخدم وفئة. تبقى الأحداث التشغيلية
ومصادرها مملوكة لوحداتها الأصلية؛ لا تنسخ وحدة الإشعارات بيانات التنبيه أو
المهمة ولا تدعي تسليم البريد قبل تأكيد backend.

### 2. المكونات الداخلية

- تطبيق Django مسجل `apps.notifications` للنماذج والخدمات وواجهات REST.
- خدمة نشر تستقبل فئة وعنوانًا ونصًا ومرجع مصدر typed، وتحدد المستلمين من
  الصلاحيات ذات الصلة وتفضيلاتهم، ثم تنشئ إشعارًا وسجل بريد outbox ذريًا.
- عامل إدارة `dispatch_pending_notifications` لتسليم البريد خارج مسار الطلب،
  مع قفل السجلات وإعادة المحاولة المحدودة بتأخير متزايد.
- مركز إشعارات شخصي في لوحة التحكم مع تعليم فردي أو جماعي كمقروء.
- موصل البريد يستخدم Django Email backend المهيأ؛ الإشعار داخل التطبيق يخزن
  في قاعدة البيانات ولا يحتاج موفرًا خارجيًا.

### 3. النماذج والحقول

- `Notification`: المستخدم المستلم، الفئة، العنوان والنص المحدودان، مرجع
  المصدر (`source_app`, `source_model`, `source_pk`) دون FK متعدد التطبيقات،
  مفتاح deduplication اختياري، و`created_at` و`read_at`.
- `NotificationDelivery`: إشعار مرتبط، قناة email، الحالة pending/sent/failed،
  عدد المحاولات، موعد المحاولة التالية، وقت التسليم، ورسالة خطأ منقحة/محدودة.
- `NotificationPreference`: المستخدم والفئة (قيد فريد)، `in_app_enabled` و
  `email_enabled`؛ الافتراضي داخل التطبيق مفعّل والبريد معطل.
- لا تحفظ بيانات اعتماد أو خرج مهام خام أو بيانات مصادر لا يحتاجها نص التنبيه.

### 4. العلاقات

- المستخدم يملك تفضيلًا واحدًا لكل فئة وعدة إشعارات، ويحذف المستخدم تفضيلاته
  وإشعاراته وفق سياسة الحساب الحالية؛ تُحفظ محاولات التسليم مع الإشعار.
- لكل إشعار صفر أو سجل بريد واحد؛ قناة in-app هي سجل الإشعار نفسه.
- مرجع المصدر typed وغير ملزم بمفتاح أجنبي لتفادي اعتماد الدورية، ويظل آمنًا
  عند حذف سجل المصدر. مفتاح deduplication فريد لكل مستلم عند وجوده.
- تُحمى سجلات التسليم من الحذف المنفصل عن إشعارها.

### 5. الخدمات ومنطق الأعمال

- النشر يتحقق من الفئة والطول والمدخلات، ولا يرسل إلا لمستخدم نشط لديه صلاحية
  مشاهدة المجال المصدر. تُطبق التفضيلات قبل إنشاء السجل؛ الإعداد الافتراضي
  إشعار داخل التطبيق، ولا يُفعّل البريد إلا باختيار المستخدم.
- ينشأ سجل email pending في المعاملة نفسها؛ لا يحدث اتصال SMTP ضمن تجميع
  القياسات أو طلب الويب. المفتاح المكرر لا ينشئ إشعارًا أو رسالة ثانية.
- عامل البريد يعالج سجلات due فقط، مع أقفال معاملات ونتيجة صريحة لكل محاولة،
  وبحد أقصى 5 محاولات وتأخير أسي. تعطيل البريد أو الحساب يوقف الرسائل التي لم
  تبدأ بعد؛ لا تمحى الأخطاء ولا يعاد تسليم رسالة مؤكدة.
- فشل إعداد البريد أو استثناء backend يسجل failed/موعد إعادة محاولة، ولا
  يصنف الإشعار delivered. لا يضم البريد إلا العنوان والنص ومرجع اللوحة.
- المستخدم لا يقرأ أو يعدل إلا إشعاراته وتفضيلاته. تعليم القراءة idempotent.

### 6. APIs والواجهات

- `GET /api/v1/notifications/`: قائمة مرقمة لمستخدم الجلسة فقط، مع `unread`
  اختياري وملخص عدد غير المقروء.
- `POST /api/v1/notifications/{id}/read/` و
  `POST /api/v1/notifications/read-all/`: تعليم كمقروء دون كشف وجود سجلات
  مستخدم آخر.
- `GET/PATCH /api/v1/notifications/preferences/`: قراءة أو تحديث التفضيلات
  الخاصة بالمستخدم؛ لا يقبل تغيير المالك أو فئات غير مسجلة.
- `/dashboard/notifications/` تعرض الإشعارات الشخصية وحالة القراءة والتصفح؛
  لا تعرض سجل email الداخلي أو معلومات مستلم آخر.
- تستخدم جميع APIs الغلاف الموحد، المصادقة والترقيم والتحقق من JSON.

### 7. الصلاحيات

- قراءة الإشعارات وتحديثها وتفضيلاتها ذاتية للمستخدم المسجل؛ لا توجد صلاحية
  مدير تسمح بقراءة إشعارات الآخرين.
- نشر إشعار خدمة داخلية فقط، وتحدد الخدمة المستلمين بناءً على صلاحية المجال:
  Monitoring، Backup، Automation/Tasks أو Security حسب الفئة.
- أوامر عامل البريد لا تقبل هوية مستلم أو محتوى حر من المستخدم.

### 8. المهام الخلفية

- `dispatch_pending_notifications` يعالج email outbox على دفعات محدودة،
  ويعمل من systemd timer أو cron كل دقيقة. تشغيل الأمر مرتين آمن بسبب الحالة
  والأقفال.
- تسجل كل محاولة وتؤجل الفشل المؤقت، وتصبح failed نهائيًا بعد الحد الأقصى؛
  لا يوقف سجل فاشل معالجة بقية الدفعة.
- لا يتطلب البريد Celery؛ إعداد عامل Django والجدولة موثق. backend غير المهيأ
  يسجل فشلًا صريحًا بدل إسقاط الإشعار.

### 9. محولات البنية التحتية

- محول البريد هو Django Email backend بإعدادات المشروع. لا يتصل التطبيق
  بمزود خارجي مباشرة ولا يضم SMTP credentials في السجلات.
- تخزين قاعدة البيانات هو قناة in-app؛ لا يُفترض وجود WebSocket أو push service
  ولا يعرض المنتج تلك القنوات قبل تنفيذها فعليًا.

### 10. الأحداث والإشعارات

- المرحلة تربط أحداث Monitoring الحالية بالنشر، وتحتفظ بحالة التنبيه الأصلية
  وتكراره في تطبيق Monitoring؛ وحدة Notifications تملك سجل التوصيل الشخصي.
- لا ترسل تنبيهات التشغيل غير المحددة بسياسات/أحداث قائمة حتى لا تنتج
  إشعارات وهمية. يمكن لوحدات Backup/Automation/Tasks استدعاء الخدمة لاحقًا
  عند وجود انتقال حالة حقيقي.
- تُنقح الأخطاء وتُحد الرسائل، وتمنع مفاتيح dedupe التكرار الناتج عن إعادة
  المعالجة.

### 11. الاعتماديات

تعتمد على Core لغلاف API والإعدادات، وAccounts للهوية والصلاحيات،
وMonitoring كمصدر أول للأحداث، وDjango Email backend للإرسال. لا تعتمد على
لوحة التحكم لتخزين أي بيانات تشغيلية ولا على Celery أو موفر realtime.

### 12. سيناريوهات القبول

- الترحيلات تنشئ نماذج الإشعار والتفضيل والتسليم بعلاقات وفهارس وقيود dedupe.
- لا يصل الإشعار إلا لمستخدم نشط ذي صلاحية المجال؛ تحقق من التفضيلات الافتراضية
  وتفضيل البريد لكل فئة وتعطيل كلتا القناتين.
- تكامل Monitoring ينشئ إشعارًا مرة واحدة لكل مفتاح؛ لا تتكرر الرسائل عند
  تكرار الحدث أو إعادة تشغيل الجامع.
- البريد الناجح يسجل sent مرة واحدة، وفشل backend/استثناءه يسجل المحاولة
  والموعد التالي، والحد الأقصى يوقف الإعادة دون إيقاف بقية الدفعة.
- API واللوحة تعزلان بيانات المستلمين وتدعمان pagination وread/read-all،
  مع اختبارات تحقق للمدخلات والصلاحيات.
- `check`, `makemigrations --check`, واختبارات الوحدة والتكامل والكاملة تنجح؛
  لا اتصال حقيقي بالبريد أو خدمات خارجية ضمن الاختبارات.

### نتيجة القبول

- اجتازت اختبارات Notifications وMonitoring المتكاملة، ونجحت مجموعة المشروع
  الكاملة: `183` اختبارًا.
- `manage.py check` و`makemigrations --check --dry-run` ناجحان. طُبقت
  `notifications.0001` و`notifications.0002` و`monitoring.0004` بعد أخذ نسخة
  من قاعدة التشغيل؛ بقيت أعداد التنبيهات والقواعد والعينات ومحاولات الجمع
  صفرًا قبل الترحيل وبعده.
- اختبرت واجهات REST واللوحة وتفضيلات المستخدم وعزل المستلمين، ومحاولات البريد
  وإعادة المحاولة عبر mocks؛ لم يُرسل بريد حي. يجب جدولة
  `dispatch_pending_notifications` والتحقق من إعداد بريد النشر قبل استخدام
  قناة البريد.

## مواصفة تنفيذ المرحلة 9: التقارير

### 1. الغرض

إتاحة تقارير تشغيلية قابلة للمعاينة والتنزيل بصيغ CSV وPDF اعتمادًا على سجلات
الخوادم والتنبيهات والمهام ونسخ الاحتياطية الموجودة. الوحدة قراءة فقط، ولا
تنشئ نسخًا من بيانات المجال ولا تعرض أسرار الاتصال أو مراجع تخزين النسخ.

### 2. المكونات الداخلية

- تطبيق `apps.reports` مسجل، مع كتالوج أنواع تقارير ثابت ومحدد في الخادم.
- خدمات selectors لكل تقرير تطبق صلاحية المصدر والمرشحات وحدود الصفوف.
- محولات تصدير CSV آمنة من حقن صيغ الجداول وPDF عبر ReportLab.
- صفحة `/dashboard/reports/` لمعاينة البيانات وتنزيل التقارير المسموح بها.
- REST API لإرجاع الكتالوج ومعاينة مرقمة وتصدير متحقق منه.

### 3. النماذج والحقول

- لا تضيف الوحدة نماذج مجال أو سجلات تشغيل أو ملفات تقارير محفوظة؛ مصدر
  الحقيقة هو `ManagedHost`, `AlertEvent`, `Task`, و`BackupArtifact`.
- تستخدم `AuditLog` القائم لتسجيل طلب التصدير، ولا تحفظ صفوف التقرير أو
  نسخة متكررة منها.

### 4. العلاقات

- لا تنشئ تقارير علاقات أو مفاتيح أجنبية جديدة. تستعلم selectors عن نماذج
  المصدر فقط وتبقي ارتباطها بمصدرها وقت كل طلب.
- تربط بيانات المصدر أسماء عرض آمنة دون إظهار credential أو `artifact_ref`
  أو سجل task الخام.

### 5. الخدمات ومنطق الأعمال

- أنواع التقارير: جرد الخوادم، سجل التنبيهات، تاريخ المهام، وبيانات metadata
  للنسخ الاحتياطية.
- التقارير الزمنية تقبل `from` و`to` بصيغة ISO-8601 مع نطاق أقصى 365 يومًا،
  ومرشح مضيف اختياري عند انطباقه. لا يقبل selector أسماء حقول أو sort حرًا.
- تعرض المعاينة حدًا أقصى 100 صف للصفحة؛ CSV حدّه 5000 صف وPDF حدّه 300 صف.
  الطلبات الأكبر ترفض برسالة خطأ واضحة ولا تنشئ ملفًا جزئيًا.
- CSV يحيّد قيم الخلايا التي تبدأ بصيغة spreadsheet، ويحد طول الخلية
  ويستخدم UTF-8 BOM لتوافق الجداول. PDF يهرب النص الديناميكي ويحتوي عنوانًا
  وتاريخ إنشاء ورقم الصفحة.
- يسجل `AuditLog` المستخدم ونوع التقرير والصيغة والمرشحات وعدد الصفوف؛ لا
  يسجل محتوى التقرير أو بيانات حساسة.

### 6. APIs والواجهات

- `GET /api/v1/reports/` كتالوج التقارير المتاحة حسب صلاحيات المستخدم.
- `GET /api/v1/reports/{slug}/?from=&to=&host=&page=&page_size=` معاينة
  مرقمة مع أسماء الحقول الثابتة.
- `GET /api/v1/reports/{slug}/export/?format=csv|pdf&from=&to=&host=`
  يعيد تنزيلًا بامتداد ونوع MIME صحيحين، أو خطأ تحقق موحدًا.
- `/dashboard/reports/` تعرض الأنواع المصرح بها والمرشحات ومعاينة فعلية
  وروابط تصدير CSV/PDF؛ لا تستخدم بيانات تجريبية أو نتائج ثابتة.

### 7. الصلاحيات

- يلزم `reports.view` لعرض الكتالوج والمعاينة، إضافة إلى صلاحية قراءة
  المجال الخاص بكل تقرير (`server.view`, `monitoring.view`, `task.view`,
  أو `backup.view`).
- يلزم `reports.export` إضافة إلى `reports.view` وصلاحية المصدر لتنزيل ملف.
- تعتمد الصلاحيات على المستخدم الفعلي، ولا تغيرها معاملات URL أو إخفاء
  خيارات الواجهة.

### 8. المهام الخلفية

- لا توجد مهام خلفية؛ التصدير متزامن ومحدود بحجم الصفوف والذاكرة. لا تخزن
  الملفات ولا تحتاج وسيطًا أو عاملًا.
- إذا تجاوز المصدر الحد المسموح يرفض الطلب؛ لا fallback لصناعة تنزيل ناقص
  أو إنشاء مهمة غير موجودة.

### 9. محولات البنية التحتية

- Django ORM للقراءة، Python CSV للملفات النصية، وReportLab لإنشاء PDF.
- لا يتصل التصدير بخدمات خارجية أو يقرأ مخزن النسخ أو ملفات النظام؛ لا يحمل
  PDF محتوى مأخوذًا من HTML غير موثوق.

### 10. الأحداث والتدقيق

- كل تنزيل ناجح ينشئ حدث تدقيق `reports.export` مع الفاعل والنوع والصيغة
  والمرشحات الآمنة وعدد الصفوف.
- فشل التحقق يعيد خطأ API واضحًا ولا يسجل كتصدير ناجح. لا ترسل الوحدة
  إشعارات ولا تنشئ أحداثًا تشغيلية.

### 11. الاعتماديات

تعتمد على Core للتدقيق وغلاف API، وAccounts للصلاحيات، وInfrastructure
وMonitoring وTasks وBackup لقراءة سجلات المصدر. تعتمد PDF على ReportLab
المعلن كاعتمادية أساسية؛ تبقى بيانات التقارير ملك الوحدات المصدرية.

### 12. سيناريوهات القبول

- API واللوحة لا تعرضان إلا الأنواع المسموح بها، وتمنعان القراءة/التصدير
  عند غياب صلاحية Reports أو صلاحية المجال المقابل.
- بيانات كل تقرير تطابق السجلات المصدرية والمرشحات الزمنية والمضيف؛ لا توجد
  صفوف أو حقول وهمية ولا أسرار أو `artifact_ref`.
- pagination ثابت، ورفض تاريخ/معرف/تنسيق غير صحيح أو نطاق يتجاوز 365 يومًا.
- CSV قابل للقراءة، UTF-8 BOM، حياد صيغ Excel وحد الصفوف وMIME/filename صحيح.
- PDF صالح كبايتات PDF، يتضمن ترويسة وتاريخًا وترقيم صفحات، ويهرب حقول المصدر.
- تسجل عمليات التنزيل الصحيحة في AuditLog فقط دون تسجيل بيانات الصفوف.
- الترحيلات لا تضيف نسخًا لمصادر البيانات؛ `check`, migration checks،
  واختبارات الوحدة والتكامل والكاملة تنجح.

### نتيجة القبول

- سُجل `apps.reports` ضمن التطبيقات والمسارات، وأضاف لوحة `/dashboard/reports/`
  المعاينة والتصدير المبنيين على API وبيانات المصدر الحقيقية.
- اكتملت تقارير الخوادم والتنبيهات والمهام والنسخ الاحتياطية، مع تقييد كل
  نوع بصلاحية المجال و`reports.view`، وتقييد التصدير أيضًا بـ`reports.export`.
- اختُبرت مرشحات الفترة والمضيف والترقيم، وتحييد خلايا CSV، وبناء PDF، وحدود
  التصدير، وإخفاء تفاصيل التنفيذ ومراجع/بصمات النسخ، وتدقيق التنزيلات.
- لا تحتوي Reports نماذج مجال أو مهام خلفية. أضيف ترحيل مراقبة إصلاحي
  `monitoring.0005` يعيد عمود إشعار التنبيه إذا كانت قاعدة البيانات قد سجلت
  `0004` دون إنشاء العمود، ويتجاوز التعديل إذا كان العمود موجودًا.
- طُبق الترحيل بنجاح على قاعدة التطوير، وتأكد وجود العمود. نجح `check` و
  `makemigrations --check --dry-run`؛ واجتازت اختبارات الإصلاح وتقارير
  Reports ومجموعة المشروع الكاملة: **197 اختبارًا**.
